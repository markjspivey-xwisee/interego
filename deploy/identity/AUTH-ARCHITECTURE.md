# Auth architecture — Interego identity

This note captures the first-principles shape of identity in Interego so future changes don't accidentally drift toward centralized conventions.

## Principles

1. **User sovereignty.** Every private key stays with the user. The server only holds public keys and verifies signatures. There are no passwords anywhere in the system.
2. **Pod as source of truth.** Each user's credential data (wallet addresses, WebAuthn credentials, DID keys) lives in their own Solid pod at `<pod>/auth-methods.jsonld`, serialized as JSON-LD against the `iep:` + `sec:` vocabularies. The identity server is **stateless** for user data; a container restart loses no durable state. Token state is likewise not in-memory: identity-server bearer tokens are HMAC-signed self-contained strings (no server-side token table), and relay-issued OAuth tokens are mirrored to a service-account pod (see OAuth 2.1 layer below). Sessions survive every redeploy.
3. **DID is canonical; userId is derived.** `did:web:<identity-host>:users:<id>` is the portable identity, and `<id>` itself is a deterministic function of the first credential enrolled (`u-pk-<hash>`, `u-eth-<addr-prefix>`, `u-did-<hash>`). **The server never trusts a user-supplied userId claim** — the only strings an unauthenticated caller can influence are their own credential material. WebAuthn, SIWE, and DID-key signatures are *verification methods* registered to that DID — interchangeable, addable, removable without identity-level disruption.
4. **W3C standards, not bespoke.** DID Core, WebID, Solid, SIWE (ERC-4361), WebAuthn, VC / Verifiable Credentials — every piece of the auth stack maps to a published standard.

## Verification methods

| Method | Key custody | First-time flow | Repeat sign-in |
|---|---|---|---|
| **SIWE** (ERC-4361) | User's Ethereum wallet (MetaMask, Coinbase, hardware, etc.) | Connect wallet → sign SIWE message with fresh nonce → server recovers address via `ethers.verifyMessage` → mints `u-eth-<addr[0:12]>` userId → writes `walletAddresses[]` to the pod (see `first-sign-in.ts`) and returns the token once the pod has it (see [Writes to auth-methods.jsonld](#writes-to-auth-methodsjsonld)) | Same signature path; `walletIndex[address]` lookup resolves user. The nonce comes from `POST /challenges` with `purpose: "siwe"`; `/auth/siwe` consumes it (single-use, 5 minutes) and requires an exact ERC-4361 message (see `siwe-message.ts`) whose domain line and URI name this deployment (this server, its relay, a `WEBAUTHN_RP_ORIGINS` origin or a `SIWE_DOMAINS` host), whose address line is the signing wallet in EIP-55 form, whose `Nonce` field is that nonce and whose `Issued At` is within 24 hours of the challenge's issue, either way. That is the only wallet sign-in: `POST /siwe/verify` and `POST /siwe/nonce` answer 410 Gone (see [Wallet proofs need a server nonce and this server's domain](#threat-model-wallet-proofs-need-a-server-nonce-and-this-servers-domain)) |
| **WebAuthn / passkey** | OS secure enclave (iCloud Keychain / Google Password Manager / hardware key) | `navigator.credentials.create` (userHandle is a transient `u-pend-<rand>` at options time) → `verifyRegistrationResponse` → server derives `u-pk-<sha256(credId)[0:12]>` → writes `webAuthnCredentials[]` to the pod and returns the token once the pod has it (see [Writes to auth-methods.jsonld](#writes-to-auth-methodsjsonld)) | Discoverable credentials: `navigator.credentials.get` with empty `allowCredentials` → `credentialIndex[response.id]` resolves the holders → each is checked against its record as the pod holds it → `verifyAuthenticationResponse`; the counter is written only when it (or the relying-party pin) changed |
| **DID Ed25519** | User-managed `did:key` or `did:web` with off-server private key | `did:key` only: client signs, with its private key, the `message` that `POST /challenges` (purpose `did-sig`) returns: a text naming this server and carrying the nonce (see *DID proofs name this server*) → server verifies with the key the DID encodes (a key of small order is refused with `400`; see *DID proofs name this server*) → mints `u-did-<sha256(did)[0:12]>` → writes `didKeys[]` to the pod (see `first-sign-in.ts`) and returns the token. Any other DID (`did:web`, …) is verified against a key the caller sends in `publicKeyMultibase`, and no DID document is fetched, so it cannot open an account: it is added from a signed-in account (bearer token) or with a bootstrap invite, and a bearer cannot add one that another account lists: `401` when a loaded account lists it with another key (the sign-in check refuses it before the bearer is looked at), `409` when the account derived from the DID lists it and is loaded only then, and `503` for any such add while accounts are loading (see *While accounts are loading*) | Same signature path; `didIndex[did]` lookup resolves user. A DID that is not a `did:key` signs in only if that account lists the same Ed25519 key for it (compared as raw bytes); when it does not, the account derived from the DID is tried before refusing |

### Writes to auth-methods.jsonld

The identity server keeps a copy of each account's record for 10 s, and reads it to decide (which accounts a wallet or DID signs in to, the epoch a token is checked against). It never writes from that copy. Every write of `<pod>/<id>/auth-methods.jsonld` (an added or removed credential, a passkey's sign counter, sign-out-everywhere, a bootstrap claim, a first sign-in, a deletion's tombstone) is one read-modify-write under that account's lock (`auth-methods-writer.ts`, `server.ts` `updateAuthMethods`; a first sign-in follows the same steps in `server.ts` `claimFirstSignInOnPod`):

1. read the record from the pod (never the copy), with its ETag;
2. apply only the change the request means, to a copy of what was read;
3. write it back conditionally: `If-Match` on that ETag, or `If-None-Match: *` when the pod had no document. A `412` means someone wrote in between (the other instance during a deploy's overlap, an operator, a request this server was answering), so the record is read again and the change applied again: at most three attempts in all (two re-reads after a `412`), for every account (a Play owner's too); then the request fails;
4. only then put what was written into the copy and the sign-in indexes, and answer.

Two writes are single conditional writes instead, under the same lock, with no retry on a `412` and no settlement after a failure (below): `/try`'s empty record for its new random id (`If-None-Match: *`; a `412` answers `503`; a failure reads the record once after it and writes nothing back, since a fence would leave an empty record behind for an id nobody will use, and when that read finds the record `/try` wrote, the write landed and the account is provisioned, otherwise `503`), and the tombstone a first sign-in leaves on a pod deleted before tombstones (conditional on the claim's own read; a `412` writes nothing and installs what the pod holds, and a failure only marks the copy stale; either way the next sign-in asks again).

So a credential removed, an epoch raised or a counter advanced elsewhere stays as it is, and a request is acknowledged only once the pod has its change. What follows from that:

- **A read that fails writes nothing** and answers `503` ("Could not read this account just now"), for every writer: a pod that cannot be read is not an account without credentials. A document that is not JSON is unreadable too: every passkey sign-in, add, removal and sign-out of that account answers `503` until an operator repairs it (this server no longer overwrites it with its copy). A wallet or DID sign-in still decides on the copy while it is under 10 s old, and on the pod once it is older: if the pod cannot be read then, the sign-in is a `503` too, never the old copy's answer.
- **A write that fails** answers with the route's error (`503` for an enrolment or a passkey sign-in, `500` for `/wallet/link`, a removal or sign-out, `503` for a deletion) and logs `WARN identity_authmethods_write_failed userId=<id> context=<what> status=<code|timeout|network>`. **Operators should alert on this line** (it replaces `identity_deferred_authmethods_failed`). Still under the lock, the write is then *settled* (`settle` in `auth-methods-writer.ts`), and the copy set to what the pod holds once the write can no longer change it. A write the pod answered (a `5xx`, a `4xx`) is over, so one read settles it, and a store that applied the write and then answered `500` leaves this server agreeing with it. A write the pod never answered (a timeout, a dropped connection) can still be applied after that read: a store keeps working on a request its client gave up on, and a read can get ahead of a queued write. So while the record is still in the state the write was conditional on (the same ETag; no document, for a create), it is written back as read on that same condition (a *fence*: an empty record, `If-None-Match: *`, where there is none), which leaves the pending write's condition unable to hold, and read again; that read is final. Without the fence, a wallet, DID or passkey whose add timed out and landed a moment later was on the pod but missing from the sign-in indexes, and a wallet's or `did:key`'s next sign-in opened the account derived from it beside the one listing it. If settling fails (a read fails, the fence gets no answer either, or the record has not moved after the fence), the copy is marked stale, which sends the next reader of that account to the pod (a token check included: it waits for that read, and uses the copy only when the read fails; it used to use the copy at once, so a sign-out-everywhere the pod applied without answering in time answered `503` and the token it ended still verified at its next use) but not a sign-in with a wallet or DID that the indexes list for no account (it reads no account's copy). A route whose write may have landed decides on the settled record: a deletion whose tombstone is there goes on and answers `200`; a bootstrap or added passkey that is there stays, and the `503` says to sign in with it; a first wallet or DID sign-in whose credential is there (a bootstrap claim's included) signs in, with the invite spent; a wallet or DID added with a bearer that is there is in the sign-in index at once, and the `503` says to sign in with it (`/wallet/link` answers `200`, linked); a removal, a sign-out-everywhere and a passkey sign-in's counter that are there answer as done (`200`, and the passkey signs in). A settled record without the change is a refusal ("Nothing was changed" where the route says so, and it is true: the fence keeps a write the pod never answered from landing afterwards). When settling failed, a first wallet or DID sign-in settles the account again once the lock is released, and a wallet or DID added with a bearer settles it once more, and each decides on that; only when that fails too does it answer `503` saying the write may or may not have been saved (and give a bootstrap invite back: a retry reads the pod first, and a credential that did land refuses any other claim), and the write is recorded so that the credential's next request settles that account before anything is decided (see *A sign-in with a wallet or DID waits for an add of it*). A removal of a wallet or DID that nothing could settle is recorded the same way (every removal that writes runs in the credential's turn; see below). A first sign-in whose write the pod refused (a `4xx`) did not land, whatever the read after it says: it answers that nothing was changed, and records nothing. Until then, opening the account derived from the credential beside the one the pod may list it on would keep the credential's sign-ins there for good. A removal, a sign-out-everywhere, a `/wallet/link` and a passkey sign-in's counter that nothing could settle answer `503` saying the same, and that repeating it is safe. A removal and a sign-out can be sent again as they are (a removal sent again removes the credential or answers `404`; a sign-out sent again ends every session again, or is refused because its token was among those ended). A link and a passkey sign-in are repeated with a new nonce or challenge, since the first request spent its own (a link repeated answers linked and writes nothing; a passkey signs in again). They used to say to check `GET /auth-methods/me`, which could not tell: while the pod is unreadable it answers this server's copy from before the write, and it is a plain read that a write still pending at the pod can overtake. A passkey added (or claimed) that nothing could settle is not recorded that way: a passkey sign-in reads only the accounts the index names, so it can answer `401` until something reads that account. A write that meets another writer's change at all three attempts, a first sign-in's included, fails the same way and logs `WARN identity_authmethods_write_conflict userId=<id> context=<what> attempts=<n>` instead; alert on it too.
- **A pod that never answers holds an account's lock for at most 15 s for a read, and 30 s for a write.** Every read and write of the record made under the lock times out after 15 s, and so does each `HEAD` a first sign-in makes before creating a derived id (*Accounts deleted before tombstones*, below). A create sends the account's container `PUT` first, with a 15 s timeout of its own, and sends no document when that gets no answer. So a pod that takes more than 15 s to answer one request fails the write, an update or a create alike (the container `PUT` used to share the document's 15 s, so a create failed on a pod taking more than about 7.5 s per `PUT`). A pod that answers slowly can hold the lock longer than the bounds above, up to 15 s for each request it answers. A hung first read, or a hung probe, ends the request; a hung write is followed by the settlement above, whose requests (a read, the fence, a read) stop at the first that fails, so it can hang for 15 s more at most. A fence that is a create (the account had no document) sends its container `PUT` first, and when that gets no answer the fence document is never sent and the settlement stops there: it used to read once more, one more timeout under the lock. A `412`, and a settlement whose requests are answered, make the writer take longer only while the pod keeps answering. A Play owner's provisioning and the janitor's purge of one make requests of their own under the lock (the purge's fence and its delete of the owner's agent registry included), each with a 15 s timeout of its own.
- **An account the indexes list is loaded before a sign-in passes it over.** Any record installed without loading its account puts what it lists into the sign-in indexes without the identity shell a load seeds: among them the settlement after a failed write, a read of an account whose add was unconfirmed (from a credential's turn, or right after the failed add), a refused first sign-in, a refused bootstrap passkey, and the record a tombstone write found changed. A passkey, wallet or DID sign-in loads such a holder first (unreadable: `503`). It used to pass it over: a passkey got `404`, and a wallet or a `did:key` opened the account derived from it beside the one listing it.
- **No read creates a document.** A read of an account whose document is missing finds no credentials; it writes nothing (it used to create an empty one, for any caller). Adding to, removing from or signing out such an account answers `404`, saying the account's sign-in record is missing from its pod (not "User for token not found", an unknown token's answer), except sign-out-everywhere for an account this server holds in memory, which creates the document so that the raised epoch outlives a restart. A Play owner's document is never re-created.
- **A passkey sign-in** checks each holder against its record as the pod holds it, and writes only the counter and relying-party pin of the passkey that verified, and only when either changed: a synced passkey reports counter 0 and its relying party is pinned at its first sign-in, so the usual sign-in is one read and no write; a counting authenticator costs one read and one write. A holder whose record cannot be read stops the sign-in (`503`), as before for Play owners and now for every holder ranked ahead of the one that verifies.
- **Adds wait for the pod.** Adding a wallet, a DID or a device with a bearer, and binding a bootstrap passkey, answer after one read and one write of the account's record (about 2.5 s on CSS, and about 1.9 s against a stand-in pod with CSS-like latencies), and adds to one account run one after another under its lock, so two at once answer after about twice that: callers with short client timeouts should allow for it. They used to answer at once (under 0.2 s) and write afterwards, and a write that then failed left a credential that this server had acknowledged and the pod never held. A wallet or DID sign-in to an account that already lists it writes nothing.
- **A sign-in with a wallet or DID waits for an add of it.** `/auth/siwe`, `/auth/did` and `/wallet/link` decide which account holds the credential, and write it onto one, in that credential's turn (`credential-decisions.ts`): on one instance, one request per wallet or DID at a time, each after the write of the one before. A sign-in made while a bearer adds the same wallet or DID (or links it) waits for that write and then signs in to the account it went to. It used to find no holder, as the indexes change only once the pod has the write (about 2.5 s on CSS), and open the account derived from the credential beside that account; the derived account is preferred, so it kept the credential's sign-ins for good. The other way round, an add or link that meets a first sign-in opening the derived account waits for it, and then finds the wallet or DID held. A turn waits at most 30 s for the ones before it, then answers `503` with nothing changed and logs `WARN identity_credential_turn_busy kind=<wallet|did> waitedMs=<n>` (no credential value). A turn held that long is a pod read or write hanging inside it, and every later request for that wallet or DID gets this `503` until it ends: **alert on it**. A DID that is not a `did:key` takes the turn only for a request that can change who holds it: an add with a bearer that verifies, or a bootstrap claim whose invite matches its seeded id. Its signature proves only the key the caller sent, so anyone can present someone's `did:web` with a key of their own, and such requests used to queue ahead of the owner's (up to the 30 s bound, then `503`); a request merely carrying a bootstrap id did too. A plain sign-in with it writes nothing and opens no account, so it is decided outside the turn. The bearer is verified once, as the request arrives, and the same answer decides both whether the request takes the turn and whether it adds the DID: a request whose bearer fails that check adds nothing (it used to check again inside, and an add that passed only the second check ran outside the turn, beside another account's add of the same DID). Such a request, and an add through `/auth/siwe` whose bearer does not verify, is refused when no account holds the wallet or DID: `503` when the bearer's account could not be read (a Play guest's bearer whose owner's record could not be read included), `401` otherwise (signed out, expired, deleted; a Play owner whose anchor does not open). It used to go on as a plain first sign-in and open the account derived from the wallet or `did:key`, which is then preferred, so the owner's retry with the same bearer signed in there and never added the credential. A bootstrap-invite claim (a wallet's, or a `did:web`'s) sent with a bearer that does not verify is refused the same way, and its invite is not spent: the claim without the bearer then succeeds. The `/connect` page sends a bearer whenever its add-device token field is filled, so a stale token left there makes an invite claim `401` until it is cleared. While a request waits for the turn (up to 30 s), its account can sign out everywhere. So every add with a bearer (through `/auth/siwe`, `/auth/did` and `/wallet/link`, and an added device between its options and its registration) checks the record it writes, and adds nothing (`401`) when that record's session epoch is above the one the bearer's token was issued at: a token signed out while its request waited completes no add. A write of the credential that stayed unconfirmed (it failed, and nothing could settle it: an add, a link, a claim, a first sign-in, or a removal) is recorded with the condition it was sent on, and the credential's next request settles that account first, in the turn (a fence, where the record has not moved, so the write cannot land after that read); for a `did:web`, a recorded write gives its next request the turn whatever that request is, a plain sign-in included. While it cannot be settled, the answer is `503` with nothing changed; once it can, the indexes show what the pod lists. A removal of a wallet or DID (`DELETE /auth-methods/me/wallet/:address`, `DELETE /auth-methods/me/did`) runs in its turn too when the account's copy lists the credential or a write of it to that account is recorded: it settles the recorded write before it reads, so an add the pod never answered cannot land after the removal has answered `404`. Any account can ask to remove any wallet or DID from itself, so a removal of one its copy does not list, with nothing recorded, does not queue in the turn: it reads the account's record outside the turn and writes nothing there, and when that record lists the credential after all (the copy was behind: the other instance or an operator added it), it runs again in the turn. So every removal that writes runs in the turn, and every one nothing could settle is recorded; one that ran outside the turn used to go unrecorded, and could land after the owner had added the credential back. Records do not stay for good: a sweep starts at most once a minute, and not while one is running, and gives each recorded credential an empty turn, one after another, which settles its account as its next request would and drops the record (a throwaway wallet whose first sign-in met a failing pod never comes back). On pods that do not answer, a pass takes about 15 s per record, so a record is visited once per pass rather than once a minute (about 42 hours per pass at the limit below). A pass that leaves records unsettled logs `WARN identity_unconfirmed_writes_unsettled left=<n>`, and a request whose turn could not settle one logs why. A write recorded against an account deleted in this process (a `u-try-` account whose record's removal failed after the write was recorded) is settled without a request to its pod: nothing read from a deleted account reaches the indexes, and its fence would be refused (it used to be tried, so the credential answered `503` until a restart). At most 10,000 are held; past that, a write nothing could settle still answers `503` "may or may not have been saved", is not recorded, and logs `WARN identity_unconfirmed_writes_full max=<n> userId=<id>`. `GET /health` reports how many are recorded (`unconfirmedWrites`). Process-local, like the account lock.
- **Concurrent sign-ins of one passkey are ordered by counter**: the second, against the record the first wrote, needs a higher counter.
- **Readers of a stale copy share one read**: one refresh per account at a time, and a refresh that waited behind a writer reuses what the writer installed (never a copy a failed write could only mark stale). A startup or on-demand load whose read a write overtook installs nothing (it reports the account as the newer record has it): a write that installed, or one that failed and could only mark the copy stale, since it may have landed.
- **The lock is not re-entrant**: a call that asks for an account's lock while it holds it throws at once (`500`) instead of waiting for itself, and a deletion writes its tombstone with the lock-free core of the same writer (a first sign-in that finds a pod deleted before tombstones writes its tombstone directly, under the lock it already holds).
- Against stock CSS 7 (the file backend), ETags are `"<modified ms>-<content type>"` and `If-Match` / `If-None-Match: *` are honoured, so the conditional write works at millisecond grain. A store that sends no ETag gets unconditional writes, which are still built on the record it holds. The fence relies on an ETag that changes on every write, which CSS's does (it is the modification time): with a store whose ETag stays the same for the same content, the read after the fence finds the record unmoved, and the write counts as unsettled. A store that sends no ETag cannot be fenced: the read after a write it never answered is taken as final.

### `did:key` encoding (Ed25519)

The server emits and accepts the W3C did:key Method Spec canonical form:

```
did:key:z<base58btc(0xed 0x01 || rawPubKey32)>
```

where `z` is the multibase base58btc prefix and `0xed 0x01` is the varint-encoded multicodec for `ed25519-pub`. A real example looks like `did:key:z6MkpTHR8VNsBx…`. The same encoding is used for the `publicKeyMultibase` field of every `Ed25519VerificationKey2020` we emit.

For back-compat with clients that registered against earlier server builds (which emitted `'z' + base64url(rawKey32)`), the decode path falls back to base64url and emits a `Deprecation: true` response header so the client can migrate. A future server version will turn this into a hard `400`.

### Three modes of first-enrollment

Every `/auth/*` endpoint picks one of three modes based on the request, and **the mode is fixed at options-time so /register cannot be coerced**:

1. **Fresh user (default).** No `Authorization` header, no `bootstrapUserId`. Server derives the userId from the credential being enrolled. Attacker cannot steal someone else's userId because the userId is a function of a keypair they don't control.
2. **Add another device to the caller's existing account.** Request carries `Authorization: Bearer <token>` for user *X*. Server binds the new credential to *X*. Used when adding a second passkey / another wallet / another DID to an existing account.
3. **Bootstrap-claim a seeded legacy userId.** Request carries `{ bootstrapUserId, bootstrapInvite }`. The invite is configured server-side in `BOOTSTRAP_INVITES=userA:tokenA,userB:tokenB` and is single-use — once consumed, or once the seeded user has any credential on file, the invite flow refuses. Used exactly once per legacy user (e.g. `markj`) to bind their very first credential to the seeded pod path. All subsequent devices for that user enroll via mode (2).

### Canonical identity lookup

- `walletIndex: address → userIds` (built from all pods' `walletAddresses[]`)
- `credentialIndex: credentialId → userIds` (built from all pods' `webAuthnCredentials[]`)
- `didIndex: did → userIds` (built from all pods' `didKeys[]`)

These indexes are rebuilt on container startup from pod scans. The authenticate endpoints *only* consult these indexes — they do not accept a userId claim in the body. If the signed credential material doesn't match an indexed entry, authentication fails.

Each index maps a credential to **every** account that lists it (`credential-index.ts`), never to one. A passkey credential id is not secret (`/challenges` with a `userId` lists that account's ids), and a software authenticator registers any id with its own key, so while a victim's account was not loaded anyone could register the victim's id: the account derived from it is empty, so a fresh registration created it. With one account per credential, whichever account loaded last owned the id, and the victim's sign-ins then failed on and off with every restart and refresh. Now a sign-in tries the holders in a stable order, at most 8 of them. The order ranks only the accounts this server has loaded; *While accounts are loading* below says what that leaves open, and what closes part of it.

- **Order.** Passkey holders, and holders of a DID that is not a `did:key`, are ordered by when the server enrolled the credential there (its `createdAt`; a record without one, written before the field existed, ranks first). A passkey is registered with `none` attestation, so its public key is whatever the registrant sends, and a public key is not secret: someone can register a copy of the owner's key under the owner's id, and the owner's signature then verifies on both accounts. The owner enrolled first, so the owner's account is tried first. A DID that is not a `did:key` is different: `/auth/did` checks a signature by the supplied key over the challenge this server issued (its message, which names this server, or, while `DID_ACCEPT_BARE_NONCE` allows it, its bare nonce) before it writes `didKeys`, so only the key's holder can bind the DID with that key. Anyone else can bind it only with a key of their own, which never verifies the owner's signature; the order keeps the owner among the first 8 tried however many such bindings pile up, and among accounts listing the DID with the same key (all bound by that key's holder) it picks the same one every time. Ties, and wallets and `did:key`s, go to the account derived from the credential, then by id.
- **Passkey:** the challenge is spent first; a challenge scoped to a `userId` tries that account only; then the first 8 holders whose record still lists the credential. More holders than that are not refused (that would let anyone who adds an id to enough accounts lock its owner out); the rest are not tried, and the log says `tried=8`. The first whose stored key verifies the assertion wins and is the only one whose counter is written. Each stored public key is tried once, at its earliest holder: the verifier refuses a sign counter at or below the stored one before it checks the signature, so a later holder storing the same key with a lower counter would otherwise accept an assertion the earlier holder refused. Keys are compared as keys (the SPKI of the decoded COSE key, `publicKeyIdentity` in `passkey-authentication.ts`), not as the stored bytes: the verifier reads the COSE map in any order and ignores labels it does not know, and a copy's registrant picks the encoding. Each holder is checked against its record as the pod holds it, under its lock, and only a changed counter or relying-party pin is written. A counter that cannot be written is a `503`, and so is a holder whose record cannot be read; either way nothing else is tried. A holder deleted during the sign-in that did not verify is skipped, not reported as the deleted account. When no holder verifies a usernameless sign-in while accounts are loading, the answer is the `503` below, not `401`. Before any holder is tried, the account derived from the id is loaded unless it is a holder already (unreadable: `503`, nothing changed): it is the account a fresh registration of the id opened, and it may list the id without being loaded, while a copy of its key on another account would be the only holder tried.
- **DID that is not a `did:key`:** the first of 8 holders that lists the DID with the key that signed, then the account derived from the DID (while accounts are loading, none of them is a `503`, not `401`). A `did:key` goes to the first loaded holder, the derived account when it is one. When another holder would be chosen, the derived account is loaded first (unreadable: `503`, nothing changed), so the choice does not change once it loads. Every account listing a `did:key` was bound by a signature from its key, so this is a deterministic choice for an ambiguity the key's holder made.
- **Wallet:** the one account listing it, or, when several do, the account derived from the wallet if it is one of them. When another holder would be chosen, or several refused, the derived account is loaded first (unreadable: `503`, nothing changed). With several holders and none derived, the sign-in is refused with `409` and the log says `kind=wallet holders=<n> refused=ambiguous`; that needs every holder loaded, since the choice is among the loaded ones (below). This server adds a wallet to an account only with a signature over its nonce, never while an account it has loaded holds the wallet (`/wallet/link` and the bearer branch of `/auth/siwe` both check), and opens or extends no account for a wallet while some account is not loaded (below). So a wallet on several accounts was bound before `/wallet/link` required this server's nonce (it took any signature the wallet had ever made, so a holder may not be the wallet's own); or by a first sign-in before this server waited for every account to load, which opened the derived account while the account listing the wallet was not loaded (below); or by the other instance during a deploy's overlap (below); or by a write to a pod from outside this server. The derived account is the one the wallet's first sign-in opens; without it, nothing says which holder is the wallet's.

**While accounts are loading.** The order protects an owner only among the accounts this server has loaded. While the owner's account is not loaded, its credential looks new: a wallet's first sign-in would open the account derived from the wallet, which then takes the wallet's sign-ins for good once the owner's account loads (the derived account is preferred); a `did:key` would do the same; and anyone could register an unloaded owner's passkey id with a copy of the owner's public key, after which the owner's usernameless sign-ins find only the copy and sign in to it. So while the index is incomplete (`/health` reports `accountIndex.complete: false`), a credential no loaded account holds opens no account, and a passkey, a wallet or a DID that is not a `did:key` joins none: a first-time `/auth/siwe` or `/auth/did` (derived or bootstrap) and every `/auth/webauthn/register-options` and `/auth/webauthn/register` (fresh, bootstrap or add-device) answer `503 Interego is still loading accounts`, write nothing, and leave a bootstrap invite unspent; adding a wallet with a bearer was already a `503` then. A passkey is refused at `/register-options`, after the bearer and invite checks and before the seeded account's pod is read, so no ceremony starts: refused only at `/register`, the browser would already have stored a discoverable passkey that no account lists, one more with every retry. `/register` refuses too, for a challenge taken from `/challenges` without the options. An account that already lists the credential is still signed in to: the first-time path reads the derived account's pod and creates nothing. That includes a wallet sign-in with `existingOnly` (the relay's `/sign-action` page), which opens nothing and adds the wallet to nothing at any time: it reads the derived account's pod like any first sign-in, and while accounts are loading a wallet it does not find there gets the `503` too, not "not registered". A DID that is not a `did:key` is not added with a bearer either (`503`): it is bound with any key the caller holds (no DID document is fetched), so a binding made while its owner's account is not loaded would not take the owner's sign-ins, since that key never verifies the owner's signature, but once the owner removed the DID (to change its key, say) the owner could not bind it again, as a DID a loaded account lists with another key is refused (`401`). A `did:key` added with a bearer is still bound, since only its key's holder can bind it. The cost: while a pod stays unreadable, new accounts and new credentials wait; the log line `identity_account_index_incomplete` names the pod, and the scan retries it each minute. A passkey added from a signed-in account or with an invite also loads the account derived from its id first (unreadable: `503`), and is refused with `409` if that account holds it.

Two things remain open:

- *Second holders that already exist.* The refusals above stop new ones. A credential two accounts already list was put there before them: a passkey copy registered before registrations waited for every account; a `did:web` another account bound with a key of its own while the owner's account was not loaded (the owner still signs in, having bound it first, but once it removes the DID it cannot bind it again until that binding is removed); a wallet linked before `/wallet/link` needed this server's nonce; or the account derived from a wallet or `did:key` that its first sign-in opened while the account listing it was not loaded (the first-time path waited 50 ms for the startup scan and then opened the account, so this could happen at any restart and while any pod was unreadable). A passkey, wallet or `did:key` sign-in loads the account derived from the credential before it picks another holder (unreadable: `503`), so an owner that is that account is never left out while it loads. The other holders are decided among the loaded ones during every startup scan, and for as long as the owner's pod stays unreadable: a passkey copy takes the usernameless sign-ins of an owner that is not the account derived from the id (one that added the passkey from a signed-in account or with an invite), a wallet that would get `409` signs in to its one loaded holder, and a `did:key` with no derived holder goes to the lowest loaded id. Once every holder is loaded, the order and the `409` hold, except for the pairs the old first-time path made: there the derived account is a holder and is preferred, so it keeps the wallet's or `did:key`'s sign-ins for good. Such an account usually lists that credential and nothing else, so removing the credential from it is refused (`409`, its last authentication method); signing in to it with that credential and deleting it (`POST /users/me/delete`, which tombstones it) hands the credential to the other holder. The startup scan logs `identity_credential_multi_holder` as it loads each such credential's second holder, a count only; finding the accounts takes a scan of the pods' `auth-methods.jsonld` (for these pairs, `u-eth-` and `u-did-` accounts whose only credential another account also lists), and removing the holders that are not the owner's closes this for them.
- *A deploy's overlap.* Old and new instances run side by side for 30 s, and what the old one writes after the new one has read the pods is not seen by the new one's index: an account opened after the new instance listed the pods, or a credential added to an account it had already loaded (its copy is re-read only when something asks for it after the 10 s cache: a sign-in or write of that account, a targeted sign-in, its token). Neither instance undoes the other's writes any more, since every write starts from the record as the pod holds it (see [Writes to auth-methods.jsonld](#writes-to-auth-methodsjsonld)); during this change's own deploy, though, the old instance still runs the old code and can overwrite the new one's writes. Until such a re-read or the next restart those credentials look new to the new instance: a wallet's first sign-in can open the account derived from the wallet, which then keeps the wallet's sign-ins even after the owner's record is re-read (the derived account is preferred), a passkey id can be registered with a copy of its key unless the account derived from the id holds it, and a `did:web` can be bound by another account with a key of its own. The other way round, a wallet or DID that the other instance, or an operator, removed still signs in here for up to 10 s after this instance last read the account (once the copy is older, the sign-in reads the pod, and is a `503` while the pod cannot be read); a passkey is always checked against the record on the pod. Two different accounts adding the same wallet with bearers at the same moment are serialised on one instance (the second finds the wallet held: see *A sign-in with a wallet or DID waits for an add of it*), but not across the two instances of a deploy's overlap.

A deleted (tombstoned) account holds nothing in the indexes, so it is never a candidate. When an account newly shares a credential with another, the log says `WARN identity_credential_multi_holder kind=<webauthn|wallet|did> holders=<n>`, a count only, at startup as much as at enrolment; for a passkey the other holder may hold a copy of the owner's key, for a `did:web` a key of its own.

A pod that cannot be read is not a pod without credentials (`account-index.ts`). The startup scan retries the listing and every unreadable pod (three more passes, at 2 s, 5 s and 15 s), then retries what is still unreadable once a minute until none is left; each read times out after 30 s. Until the scan is complete, a passkey that matches no loaded account gets `503 Interego is still loading accounts` rather than `401`, so nobody is told to register again. A targeted sign-in (`/challenges` with a `userId`) and a token whose account is not in memory both load that account from its pod on demand: an unreadable pod there is a `503`, never "No passkey found" or "User for token not found". `GET /health` reports `accountIndex: { complete, listed, unreadable, lastPassAt }`, and the log line `identity_account_index_incomplete` says which pods are still unread. Before this, every failed read counted as "no credentials": a restart while CSS was slow left 437 of 445 accounts unknown, which disconnected their connectors and refused their passkeys.

## OAuth 2.1 layer

- DCR (RFC 7591) on `/register` — no client pre-registration required.
- Authorization code + PKCE mandatory — public clients only, no client secrets.
- Identity-backed `/authorize` page renders method-picker HTML; browser JS runs the signature ceremony against the identity server's `/auth/*` endpoints.
- On successful verification, the relay issues:
  - **Access token** (1h TTL) carrying the user's { userId, agentId, ownerWebId, podUrl } in the token's `extra` field — MCP handlers attribute writes to the real user.
  - **Refresh token** (14d TTL, rotating on every use) for long-running sessions.
- **Relay token persistence.** Access + refresh tokens are mirrored to the `svc-relay-dcr` service-account pod under sibling `tokens/` and `tokens-refresh/` subcontainers. Filenames are `sha256(token).hex` so the raw bearer never lands on disk; the OAuth provider exposes swappable `persistAccessToken` / `removeAccessToken` / `lookupAccessTokenByRaw` (and refresh-token equivalents) hooks. Existing claude.ai / ChatGPT sessions survive relay redeploys instead of 401-ing until reauthorized.
- **Identity-server tokens are stateless HMAC-signed strings.** Format: `cg2_<base64url(payload)>.<base64url(hmac-sha256)>`, signed with `TOKEN_SIGNING_KEY` (stable across deploys). Payload carries `{ userId, agentId, scope, issuedAt, expiresAt, epoch }`. There is no in-memory token Map — verification is signature check (`timingSafeEqual`) + expiry + identity-presence + `sessionEpoch` check against the user's `auth-methods.jsonld`. Revocation is per-user: `POST /tokens/me/sign-out-everywhere` increments the pod's `sessionEpoch`, instantly invalidating every prior token for that user without a global flush.
- `/.well-known/oauth-authorization-server` and `/.well-known/oauth-protected-resource` let any MCP client auto-discover the auth flow.

### Discovery endpoints — WebFinger (RFC 7033)

The identity server mounts RFC 7033 WebFinger at `/.well-known/webfinger` (see `deploy/identity/webfinger.ts` and `server.ts:3182`). It is the discovery surface that lets an `acct:user@host` handle resolve to the user's WebID, did:web, and pod URL — and is used by `share_with`, the name service, and federation discovery.

- **Resource form.** `?resource=acct:<userId>@<host>` (RFC 7033 §4.5). HTTP(S) courtesy forms `https://<host>/users/<id>` and `https://<host>/agents/<id>` are also accepted.
- **Optional rel filter.** Repeated `?rel=<rel>` filters `links[]` only (RFC 7033 §4.3); `aliases` are unchanged.
- **Content type.** `application/jrd+json` (RFC 7033 §4.4). 404 responses carry an empty body.
- **Canonical `subject`.** The `subject` in every successful response is the canonical `acct:<userId>@<host>` — never the displayName the requester sent — so federation crawlers converge on one form per identity. If the caller used a displayName alias (e.g. `acct:markj@host` resolving to `u-pk-…`), the displayName form is added to `aliases[]` instead of replacing `subject`.
- **User JRD shape.**
  - `aliases`: `[ <webId>, did:web:<host>:users:<id>, <podUrl> ]` (plus the displayName `acct:` form if used).
  - `links`:
    - `http://webfinger.net/rel/profile-page` (`text/turtle`) → WebID profile
    - `http://www.w3.org/ns/pim/space#storage` → pod root URL
    - `http://www.w3.org/ns/solid/terms#oidcIssuer` → identity server base URL
    - `self` (`application/did+ld+json`) → DID document
- **Agent JRD shape.** Similar, plus `prov:actedOnBehalfOf` linking to the owner's WebID.

## Token introspection: who may ask whether a token is live

`POST /tokens/verify` takes `{ token }` and answers whether an identity token is live: `{ valid: true, userId, agentId, scope, expiresAt, ownerDid, webId, podUrl }` for one this server signed and that still verifies, otherwise `{ valid: false, reason }`. Forging a token is already prevented by `TOKEN_SIGNING_KEY`; what the route adds for someone holding a captured token is whether it is still live (not expired, revoked or deleted). It has two callers:

- the relay (`deploy/mcp-relay/server.ts`, `verifyBearerToken`), for identity tokens on REST `/tool/<name>`, `/messages`, `/client-interactions`, A2A calls and provisional-play calls;
- css-gate (`deploy/css-gate/server.mjs`), for writes and for owner reads of each pod's private documents.

Both send `Authorization: Bearer <IDENTITY_INTROSPECTION_SECRET>` whenever their own copy of that variable is non-empty (the relay reads it on every call, css-gate at start). Not to be confused with the relay's own `POST /verify-token` and its `RELAY_INTROSPECTION_SECRET`, which css-gate uses for the relay's OAuth tokens.

The identity server reads two variables at startup and runs in one of three modes:

| Identity env | `GET /health` | `POST /tokens/verify` |
|---|---|---|
| `IDENTITY_INTROSPECTION_SECRET` set (`ALLOW_OPEN_INTROSPECTION` ignored) | `introspection: "enforced"`, `allowOpenIntrospection` says whether `ALLOW_OPEN_INTROSPECTION=1` is still set | Answers only `Authorization: Bearer <secret>`. No bearer, or another scheme: 401 `introspection bearer required`. A wrong value: 401 `introspection bearer rejected`. The scheme is case-sensitive (`bearer <secret>` counts as no bearer). |
| No secret, `ALLOW_OPEN_INTROSPECTION=1` | `introspection: "open"`, `allowOpenIntrospection: true` | Answers anyone; the startup log warns. |
| Neither | `introspection: "disabled"`, `allowOpenIntrospection: false` | 401 `token introspection is disabled — …` for everyone, which refuses both callers. |

The startup log says which: `Introspection: ENFORCED`, the `OPEN mode` warning, or `Introspection: FAIL-CLOSED`. The relay's `GET /health` and css-gate's `GET /healthz` report `identityVerifyAuth`, whether they present a bearer. css-gate also reports `identityVerifyResults`, how identity has answered its verify requests since the gate started: `accepted` (identity answered 2xx, whatever it said about the token), `refused` (401 or 403: identity refused the gate's bearer), `other`. Nothing reports the value, its length or a hash of it.

**The value.** One value on three services: `relay`, `css-gate` and `identity`. Use 32 random bytes as hex (the rollout workflow generates exactly that, and refuses a stored value that is not printable ASCII without spaces, or shorter than 32 characters). A value that ends in a space or tab, or holds an ASCII control character other than TAB (U+0000-U+001F or U+007F) or a character above U+00FF, cannot be sent intact in a header, so identity refuses every caller; identity's startup log and css-gate's warn about exactly those values, without showing them. Leading or interior spaces and tabs, and other Latin-1 characters (the C1 controls U+0080-U+009F among them), arrive intact, so they draw no warning.

**Rate limits.** A request presenting the right bearer counts against the `introspection` budget, 600 a minute per address. Every other request to this route counts against the shared per-address `tokens` budget, 60 a minute, with `POST /tokens`, `POST /register-agent`, `POST /tokens/me/sign-out-everywhere`, `POST /users/me/delete` and `GET /agents/me`, before it is answered. An address that has used its 60 gets 429 even with the right bearer, so a guess at the secret past the 60th learns nothing.

### Rollout

With `.github/workflows/identity-introspection-provision.yml` (`tools/identity-introspection-provision.mjs`), one stage per dispatch, a dry run first each time (it reports names, set or unset, and `equal: yes/no`). The tool writes only when the workflow runs it on master; run locally, it does dry runs only.

Every stage refuses ("deploy master first") until all three services run a build that reports the health fields above: identity's `GET /health` reports `introspection` and `allowOpenIntrospection`, the relay's `GET /health` reports `identityVerifyAuth`, and css-gate's `GET /healthz` reports `identityVerifyAuth` and `identityVerifyResults`. So the first step is to deploy master to the three services and check those fields. Then:

1. `stage=callers`: generates one value and writes it to the relay and css-gate, then deploys both with the image they already run and waits until each reports `identityVerifyAuth: true`. Identity is still open, so nothing changes for users.
2. `stage=identity`: checks that identity accepts both callers now, copies their value to identity (keeping `ALLOW_OPEN_INTROSPECTION`, the rollback; it refuses to write while identity does not store `ALLOW_OPEN_INTROSPECTION=1`, since deleting the secret again would then leave introspection disabled; identity opens only on exactly `1`, so any other stored value counts as not stored), deploys identity, waits until it reports `introspection: "enforced"` (and, when the rollback was stored, still `allowOpenIntrospection: true`; a deployment without it fails the stage and says to set `ALLOW_OPEN_INTROSPECTION=1` before deleting the secret), waits out the deploy's overlap, and checks again that identity accepts the relay and css-gate. A refusal fails the job and names the rollback. The check before the write cannot tell which value a caller runs, because an open identity accepts any: a caller whose variable was changed in Railway without a deploy runs a value other than the one this stage copies, identity refuses it once the deploy enforces, and only the check after the deploy finds that. To rule it out beforehand, deploy any caller whose variable may have changed since its last deploy (the dashboard's Deploy, or `deploy-railway.yml` with its current build sha) before this stage; while identity is open that changes nothing for users.
3. `stage=finalize`, after an observation window: removes `ALLOW_OPEN_INTROSPECTION` (whatever its value) from identity and deploys it, until `allowOpenIntrospection: false`, then waits out the deploy's overlap and checks again that identity accepts the relay and css-gate. The new container enforces the value Railway stores, which can differ from the one the old container ran (a value changed without a deploy), so a refusal fails the job with the after-finalize rollback below.

Each upsert passes `skipDeploys: true`, and the tool then deploys the service itself with the image it already runs. The finalize delete has no such option, so after it the tool follows the deployment Railway starts, or starts one. The tool refuses before writing when a service serves a build other than its pin, a deployment is in flight, a service reports the variable while Railway shows it unset (sealed, or deleted without a deploy, whose next deploy ships it unset: the refusal says to restore a deleted one before anything deploys that service), or an `Auto-deploy master` or `Deploy to Railway` run, or another run of this workflow, has not finished. Stages `identity` and `finalize` also refuse while css-gate is set to anything other than one replica: their check that identity accepts css-gate compares two readings of css-gate's `identityVerifyResults`, which each replica counts for itself, and two readings from different replicas can make that check wrong either way, including reporting a refused gate as accepted. Do not dispatch while either deploy workflow is running, and dispatch one run of this workflow at a time: a second dispatch queued before the first passes its checks makes the first refuse. The tool writes only when this workflow runs it on master (it checks `GITHUB_ACTIONS`, `GITHUB_REF` and `GITHUB_WORKFLOW_REF`). That stops an accidental apply, not someone who holds `RAILWAY_PROJECT_TOKEN`: it is a repository secret, which a workflow pushed to any branch can read, and such a workflow can set those variables too. Inside Actions the tool registers the value it generates, and each stored value it reads that could be the secret (32 or more printable ASCII characters without spaces), with the runner's `::add-mask::` command, which hides them from the job's log. A shorter stored value, or one with a space, is not registered, because masking a short string such as `1` hides every occurrence of it in the log; the tool refuses such a value and prints none either way. The add-mask line carries the value to stdout, so run the tool with `GITHUB_ACTIONS=true` only on a runner. Optional checks after stage 2: `GET https://gate.interego.xwisee.com/<your userId>/auth-methods.jsonld` with your own identity token (never pasted anywhere) answers 200; a 401 `token not found or expired` means the gate's value is wrong, and the gate caches that refusal for 60 s. `client-signature-live.yml` drives the relay's `/client-interactions` with an identity token.

### Rollback, floors and rotation

- **Before finalize:** delete `IDENTITY_INTROSPECTION_SECRET` from identity and deploy identity (the dashboard's Deploy, or `deploy-railway.yml` with `service=identity` and its current build sha). With `ALLOW_OPEN_INTROSPECTION=1` still set, identity is open again. Confirm that identity's `GET /health` reports `introspection: "open"` on two readings in a row. Its `build` is the same before and after, so it cannot tell the containers apart, and the old one keeps answering for the deploy's overlap after SUCCESS.
- **After finalize:** set `ALLOW_OPEN_INTROSPECTION=1` first, then delete the secret and deploy identity as above, and confirm `introspection: "open"`. Deleting the secret without `ALLOW_OPEN_INTROSPECTION=1` leaves introspection disabled (`introspection: "disabled"`), which refuses both callers.
- **Rollback floors.** Once identity enforces, the relay must run `f20b8499` or later and css-gate `9ce7812f` or later: older images send no header and are refused. That holds however an older image is deployed. To run an older caller image, use `deploy-railway.yml` with its tag, which keeps the service's current variables.
- **Railway's Rollback restores variables too.** A Rollback in the Railway dashboard restores the chosen deployment's variables as well as its image ("Both the Docker image and custom variables are restored", [Railway, Deployment Actions](https://docs.railway.com/deployments/deployment-actions)), so the image floors are not the only thing it can get wrong.
  - Every relay and css-gate deployment made before `stage=callers` has `IDENTITY_INTROSPECTION_SECRET` unset, whatever its image. Once identity enforces, do not roll either caller back past the deployment `stage=callers` made. A caller rolled back that far sends no header and identity refuses it: the relay's REST writes, `/messages` and `/client-interactions` with an identity token fail, and so do css-gate's writes with one. If it happens, undo it at once: in Railway, roll that caller back again to the deployment that was active before the rollback, which brings the variable back, and wait for `identityVerifyAuth: true`. Do not delete the other caller's copy. While Railway shows the variable unset on the rolled-back caller, every stage of the workflow refuses and says the same, whatever image the Rollback restored, also when the relay's or identity's variable is sealed: the refusal comes before the ones about the image (a pin that is not a sha, a build other than the pin, an image without the health fields), which would say to deploy master or reconcile with `deploy-railway.yml`, and deploying keeps the restored, unset variable. When the caller's health does not answer, or does not report `identityVerifyAuth` (an image older than the health fields), the tool cannot tell a rolled-back caller from one whose variable is sealed or was deleted without a deploy, so the refusal names all three: if it is sealed, rerun once its health answers; if its variable was deleted without a deploy, its next deploy (an auto-deploy included) ships it unset and identity refuses it, so restore the variable before anything deploys that caller; if a Rollback took it past `stage=callers`, roll it back again. (A deployment still in flight is refused first; rerun when it has finished.)
  - Rolling identity back past the deployment `stage=identity` made restores an identity without the secret: with `ALLOW_OPEN_INTROSPECTION=1` it is open again (`introspection: "open"`), and without it disabled. Rolling it back past the deployment `stage=finalize` made, but not past `stage=identity`'s, restores `ALLOW_OPEN_INTROSPECTION=1` (`allowOpenIntrospection: true`); identity still enforces.
  - After any Rollback of the three services, check the health fields: `identityVerifyAuth` on the relay's `GET /health` and css-gate's `GET /healthz`, and `introspection` and `allowOpenIntrospection` on identity's `GET /health`.
- **Rotation.** Identity accepts one value, so changing it means a brief failure for whichever side runs the old value until all three run the new one. The tool refuses differing values and does not rotate; accepting two values at once would need code.
- **Sealing.** Seal the variable only after finalize, if at all. Railway does not return a sealed value through the API, so the tool then sees the variable unset while the service reports it, and refuses. It cannot tell that from a variable deleted without a deploy, which the service's next deploy (an auto-deploy included) ships unset, so the refusal names both and says to restore a deleted variable before anything deploys that service.
- **By hand,** only when the workflow cannot run; the workflow is the supported path, because it never puts the value in a file. Create the value in a file only you can read, on a memory-backed filesystem: `(umask 077; openssl rand -hex 32 > /dev/shm/iis)`. For `relay`, then `css-gate` (wait until each reports `identityVerifyAuth: true`), then `identity` (wait for `introspection: "enforced"`, then make the optional checks above), run `RAILWAY_PROJECT_TOKEN=... node tools/railway-set-secret-var.mjs <service> IDENTITY_INTROSPECTION_SECRET /dev/shm/iis`, a dry run that shows whether that service already holds the file's value, then the same command with `--apply`. Then delete the file (`rm /dev/shm/iis`). The tool prints a length and a 12-hex SHA-256 fingerprint and never the value. It does not print Railway's error text either, which can quote the value: a failed request prints one line naming the step, and when the write itself failed, the same command without `--apply` shows whether Railway holds the file's value. An `--apply` that writes makes Railway redeploy that service. One whose dry run said `no change needed` writes nothing and starts no deploy, so if the service's health field still does not show the change (a value stored earlier whose deploy failed or never ran), deploy the service yourself: the dashboard's Deploy, or `deploy-railway.yml` with its current build sha. To finalize, remove `ALLOW_OPEN_INTROSPECTION` from identity in the Railway dashboard, deploy identity, and wait for `allowOpenIntrospection: false`.

## Threat model: userId-claim hijack (closed)

A naïve implementation would let a caller type *any* userId on the enrollment page and bind their own credential to it. That pattern let an attacker who learned a display-alias like `markj` attach their passkey to the real user's account, issue bearer tokens for them, and — because the passkey went into the pod's `auth-methods.jsonld` — survive container restarts indistinguishably from legitimate credentials.

The current code closes this by removing user-supplied userId claims everywhere:

- `/auth/webauthn/register-options` no longer accepts `userId`. It accepts a display `name` and optional bootstrap/bearer proof. The WebAuthn `userHandle` is a transient `u-pend-<rand>` unless mode (2) or (3) applies.
- `/auth/webauthn/register` derives the final userId from the credential itself and binds it to a seeded userId *only* if a matching single-use bootstrap invite was already validated at options time. A registration without a bearer or invite may only *create* the derived account: the server reads that pod first and answers `409` if it already holds any credential (credential ids are not secret, and the derived id is 48 bits), `503` if the pod cannot be read, and writes a missing account with `If-None-Match: *`. After a refusal, or a write the pod did not confirm, it loads whatever account the pod holds (no token), so a passkey whose write did land can still sign in.
- `/auth/siwe` and `/auth/did` follow the same three-mode pattern — userId is derived from address / DID unless a bearer token or bootstrap invite authorises binding to a different user.
- `/auth/webauthn/authenticate` resolves the user via `credentialIndex[response.id]` (the first holder whose key verifies, above), ignoring any body-supplied userId hint.
- `/register` now returns **410 Gone** — there is no reason to reserve a userId without proving key-ownership.
- `/wallet/link` now requires `Authorization: Bearer <token>` and binds to the token's user (the previous unauthenticated variant let any caller attach a foreign wallet to any user's account).

## Threat model: wallet proofs need a server nonce and this server's domain

A wallet signature proves only that the wallet signed *that text*. Unless the text carries a single-use nonce this server issued, it may have been signed for anything: a SIWE sign-in to another site, a message posted publicly, a signature on-chain. Anyone holding such a message can present it again.

A server nonce is necessary but not enough. Anyone can fetch one from `POST /challenges` and put it in their own site's "Sign in with Ethereum" prompt: `evil.example wants you to sign in with your Ethereum account: … Nonce: <our nonce>`. The wallet compares that domain line with the page asking and sees no mismatch, so the user signs, and the message comes back to this server carrying a nonce it issued. What ties a signature to an Interego sign-in is the domain line, so both wallet routes require it to name this deployment:

- The accepted hosts are this server (`BASE_URL`), the relay (`RELAY_URL`, `RELAY_PUBLIC_URL`), the `WEBAUTHN_RP_ORIGINS` origins, and any host in `SIWE_DOMAINS` (comma-separated, for another front-end of the same deployment): only hosts the operator set. The relay host that `relayPublicBase()` guesses from `BASE_URL` when `RELAY_PUBLIC_URL` is unset (`identity.` → `relay.`, `-identity.` → `-relay.`) is not accepted: on a shared hosting suffix that name may be anyone's, and a page an attacker serves on an accepted host passes the wallet's own domain check too. The server logs each accepted host at startup with the setting it came from.
- The domain line only protects anyone if the wallet reads the message as Sign-In with Ethereum, because that is when it compares the domain with the page. MetaMask does this only for text `@spruceid/siwe-parser` parses; anything else is a plain signature request with no warning. So the server accepts exactly ERC-4361 and nothing looser (`parseSiweMessage` in `siwe-message.ts`, checked against siwe-parser in `tests/siwe-message.test.ts`): LF line ends, no leading or trailing whitespace, the address in EIP-55 form, the fields in order (URI, `Version: 1`, Chain ID, Nonce, Issued At, then the optional ones), the nonce read from the `Nonce` field, each URI and resource RFC 3986 part by part as siwe-parser reads it (no `[` `]`, one `#` at most, a host on the `URI` line) and a `Request ID` of pchar only. The URI's host must be an accepted host too. `Issued At` must be within 24 hours of the challenge's issue, either way: it is the signing device's clock, and freshness is the single-use, five-minute nonce's job. The window used to be the challenge's issue to now, give or take five minutes, which refused sign-ins from any device whose clock was more than five minutes off and kept out nothing the nonce did not. `Expiration Time`, if present, must not have passed by this server's clock, and `Not Before` must be no more than five minutes ahead of it. Before, the server trimmed the first line (which also strips a byte-order mark), took a `Nonce:` line anywhere and required no other field, so an attacker could pick a form the server took and the wallet did not treat as a sign-in.
- `POST /challenges` with `purpose: "siwe"` issues a hex nonce (ERC-4361 allows letters and digits only; a base64url nonce's `-` or `_` made the message unreadable to the wallet). Sent `address`, it returns that address in EIP-55 form: a browser gets lowercase addresses from `eth_requestAccounts` and has no keccak-256 to checksum them, so `/connect`, the relay's `/authorize` page and `client-sign.html` sign the form it returns. Because the relay serves the `/authorize` page and a copy of `client-sign.html`, roll the relay out before the identity server that enforces EIP-55: the new pages work against an older identity server (they fall back to the wallet's own address), but the older pages sign a lowercase address the new server refuses.
- A message whose first line names any other host is refused with 400 and its nonce is spent. The host appearing only in the statement does not count: the domain line is what the wallet showed the user.
- The second line must be the address the signature recovers to (401 otherwise).

Before 2026-10-26 `/auth/siwe` checked only that the message contained the nonce somewhere, so the relayed prompt above signed in. The routes, as they are now:

- `POST /siwe/verify` checked only that a signature over any message containing the address recovered to that address, with no nonce, nothing consumed and no domain, and then issued a `ReadWrite` token for the wallet's account. Replaying one message the victim's wallet had ever signed took over the account. It now answers **410 Gone** with a pointer to `POST /challenges` (`purpose: "siwe"`) and `POST /auth/siwe`, verifies nothing and issues nothing (still rate-limited). `POST /siwe/nonce`, which returned random bytes nothing stored, answers 410 the same way. Nothing in this repository called either.
- `POST /wallet/link` (bearer-authenticated as the linking account) accepted a signature over any message and linked a wallet another account already held, so an attacker with an account of their own and one signature by a victim's wallet could attach that wallet to the attacker's account. It now takes `{ walletAddress, siweMessage, signature, nonce }`:
  - `nonce` comes from `POST /challenges` with `purpose: "siwe"` and is consumed as `/auth/siwe` consumes it: single-use, 5 minutes. It is spent as soon as the body is read, before the bearer is checked, so a request refused for any reason (a stale bearer, say) leaves no message and signature that `/auth/siwe` would still accept. Missing → 400; unknown, expired, used or of another purpose → 401.
  - The message follows the same rule as `/auth/siwe` (exact ERC-4361 naming this deployment, with that nonce in its `Nonce` field), and its address line is `walletAddress`. Otherwise → 400. The signature must recover to `walletAddress` → otherwise 401.
  - A wallet another account holds is refused with **409**, as for passkeys and DIDs. The account the wallet would have opened by itself (`u-eth-<addr[0:12]>`) is loaded from its pod first in case the index missed it, and while any pod is unreadable (the account index is incomplete) the route answers 503 and changes nothing, since it cannot tell who holds the wallet.
  - The stdio MCP server's `link_wallet` tool follows the `/wallet/link` rule: its first call fetches the nonce (and the address in EIP-55 form) from `/challenges` and shows the message with a `cast` command quoted so the shell passes its newlines, its second call submits that same message with the nonce and the bearer in `CG_IDENTITY_TOKEN`. Without a bearer configured it says so and sends nothing.
- `POST /auth/siwe` with a bearer adds the wallet to the bearer's account only when no account holds it, checked the same way (`walletHolder` in `server.ts`). A wallet held by an account found only on its pod signs in to that account, exactly as an indexed one does, and while the holder cannot be ruled out (its derived account's pod is unreadable, or the account index is incomplete) it answers 503 and binds nothing. Before, a wallet missing from the index was bound to the bearer's account outright.

### DID proofs name this server

A DID key signs whatever text it is given, and a signature over a bare nonce names no server. `/auth/did` used to verify an Ed25519 signature over the `/challenges` nonce alone. Now `POST /challenges` with `purpose: "did-sig"` returns `message` beside the nonce, and `/auth/did` verifies the signature over that text:

```
Interego DID sign-in v1
Host: <host>
Nonce: <nonce>
```

- LF line breaks, no trailing newline, ASCII only. The first line says what the text is and its format version, which sets it apart from anything else an Interego key signs; `Host` names the verifier; `Nonce` makes the text single-use.
- `Host` is `new URL(BASE_URL).host`, with the port when it is not the scheme's default: the `base` that `/health` reports. It never comes from a request header (`Host`, `X-Forwarded-Host`, `Forwarded`, `Origin`), and nothing else in the text comes from the request. The DID is not in it: no client sends one to `/challenges`, binding it would put requester-chosen text into bytes that automated clients sign without reading, and `/auth/did` already ties the signature to the DID's key (a `did:key` is its key; any other DID's key is checked against the account). A later version of the text can add it.
- The message is stored with the challenge, and `/auth/did` verifies the signature over exactly the bytes `/challenges` returned; nothing rebuilds the text at sign-in, so what is signed and what is checked cannot differ. Only a `did-sig` challenge carries a message.
- The client signs `message` byte for byte, as UTF-8, and never builds it from its parts. On the relay's `/authorize` page the base64url field holds the exact bytes, and the `Host` line should equal the `identity:` host in the page's footer.
- Refused with 401 whatever the setting below, with "Ed25519 signature verification failed. Sign, with the DID's key, the exact UTF-8 bytes of the message …": a signature over a message naming another host, over another challenge's message, or over the message with anything changed (CRLF line breaks, a trailing newline, whitespace trimmed or added, a byte-order mark, another version line), or by another key. The nonce is spent by then, as by every refusal once the challenge is found, so a corrected retry needs a new challenge. A nonce of another purpose is refused with "Invalid or expired challenge" and left as it was, as before. Single use, the five-minute expiry, bootstrap invites (a refused proof spends none), the multi-holder order, tombstones and the rate limits are unchanged.
- Refused with 400 before any signature is checked, whatever the setting below, with "This is not a usable Ed25519 key: it is a point of small order …": a key of small order, whether a `did:key` names it or `publicKeyMultibase` carries it, in any of its encodings (`isSmallOrderEd25519Key` in `did-parse.ts`, the list libsodium refuses). A signature by such a key can be made without a private key, so none of the refusals above would hold for it, and OpenSSL's verify does not refuse one. No key generator makes such a key. The nonce is spent, as by a key that does not decode.
- What this protects: a signer that reads or checks the text it signs (a person, or a tool that signs only text it recognises) now sees which server it is signing in to. A signer that signs any string handed to it is protected only by signing nothing but challenges it asked for itself. The clients in this repository sign the `message` they are handed and do not yet compare its `Host` line with the identity server they called.

**Transition: `DID_ACCEPT_BARE_NONCE`.** A client that still signs the bare nonce keeps working while the setting allows it:

- Unset or `1` (the default for now): accepted, with `Deprecation: true` and a `Warning` header for a direct caller (the relay passes on only the `error` and the token), and one log line per sign-in made this way:
  ```
  [identity] WARN identity_did_bare_nonce outcome=accepted purpose=did-sig method=key derivedUserId=u-did-… userId=u-did-… surface=mcp-client ua="node" origin=-
  ```
  `purpose` is `did-sig`, or `none` for a challenge taken with no purpose, which has no message and signs in only this way. `method` is the DID method. `derivedUserId` is the account derived from the DID, and `userId` the account signed in to, which can differ (a bearer add, or a DID another account bound first). `surface` is the request's `surfaceAgent` when it is a slug (`invalid` when it is not, `-` when absent); `ua` and `origin` are the request's headers, quoted. The line never carries the DID, the nonce, the signature, an invite or a token. It is written once the sign-in is done, as its token is issued. A signature over the bare nonce whose sign-in is refused on the way (a key no account lists for this DID, a pod that cannot be read) writes no line, as that refusal does not depend on the setting. `surface` and `ua` are what the caller claims; a call through the relay shows `ua="node"`, no origin, and the relay's surface slug.
- `0`: refused with 401, "This signature is over the bare nonce, which names no server. … The challenge is spent; request a new one.", and logged the same way with `outcome=refused` and `userId=-`. That line is written at the signature check, before any account is looked up: for a `did:key` the DID's own key signed, but for any other DID the key is the caller's, so its `derivedUserId` names whatever DID was sent. Nothing is written and no invite is spent.
- Surrounding whitespace is ignored, and an empty value counts as unset. Any other value stops the server at startup. The startup log says which setting is in force.

The `/auth/did` log lines quote the DID and the other values a caller sends (the surface hint, the display name, and the agent id and label made from them, also in the lines that seed a new identity and issue its token), as JSON strings with anything outside printable ASCII shown as `?`. The server writes a line break inside any log entry as an indented continuation, and a timing line replaces it with `?`, so nothing a caller sends starts a log line that reads like this one. A line break here is any character a log reader may end a line at: CR, LF, VT, FF, U+001C to U+001E, U+0085, U+2028 and U+2029 (the set Python's `str.splitlines` uses). The continuation is what covers the first-sign-in lines of a wallet and a passkey, which print the surface hint and the agent id made from it as sent. It still carries the caller's text, after four spaces, and a quoted value can hold any printable text, so count only lines that begin with `[identity] WARN identity_did_bare_nonce` (in a log reader that prints a column before each line, directly after that column: see below): a search that matches anywhere in a line also finds such text. The `did-verify` timing line (`IDENTITY_TIMING=1`) also says which proof verified: `proof=message`, `bare-nonce` or `none`.

Set `DID_ACCEPT_BARE_NONCE=0` once no `accepted` line names a known client, counting only lines that begin as above. Anyone can produce such lines with a fresh `did:key`, so the count may never reach zero: judge by `surface`, `ua` and the account signed in to. That account is the `userId=` field directly after `derivedUserId=`, which names an account only after a sign-in to it, and that takes the account's own credential (its DID key, a bearer token for it) or its bootstrap invite. `ua` and `origin` are quoted caller text and can hold `userId=…` as well, so read the field by its position, for instance with `^\[identity\] WARN identity_did_bare_nonce outcome=accepted purpose=\S+ method=\S+ derivedUserId=\S+ userId=(\S+) surface=`; a search for `userId=` anywhere in a line also finds what a caller wrote. That pattern reads the lines as the server writes them. The repository's reader, `npx tsx tools/railway-logs.ts identity --filter identity_did_bare_nonce`, prints each line after its timestamp and two spaces, so the pattern as given matches none of its output, real lines included, and a count made that way reads zero while clients still sign in over the bare nonce. There a line counts only when the prefix comes directly after that column: match `^\S+  \[identity\] WARN identity_did_bare_nonce outcome=accepted purpose=\S+ method=\S+ derivedUserId=\S+ userId=(\S+) surface=`, or strip the column first with `sed -E 's/^\S+  //'` and use the pattern above unchanged. A continuation shows there as six spaces after the timestamp, which neither matches. Do not make the pattern fit by dropping its `^`: unanchored, it also matches a continuation and a quoted value, and counts the `userId=` a caller wrote there. Set it as a variable of the Railway `identity` service, which a redeploy keeps: `node tools/railway-set-var.mjs identity DID_ACCEPT_BARE_NONCE 0` shows the change and the same command with `--apply` writes it. Writing it also redeploys the service: the tool's header says it does not redeploy, but its `variableUpsert` sends no `skipDeploys`, so Railway deploys the service with the new value as soon as it is written. Wait for that deploy rather than restarting the service again (each restart drops the challenges held in memory and reloads the account index), then check that its startup log says `DID sign-in: a signature over the bare nonce is refused (DID_ACCEPT_BARE_NONCE=0)`. A later change removes the bare-nonce path and the setting, and requires purpose `did-sig` at `/auth/did`.

Deploy order: the clients went first (the relay's `/authorize` page, the bridges that mint relay tokens with a DID key, the workflows and scripts), and the default makes this server step safe on its own. Before the setting is flipped, the relay and every such bridge must run the clients that sign `message`.

### Bootstrap invite configuration

```bash
BOOTSTRAP_INVITES="markj:<long-random-token>,alice:<another-token>"
```

- Tokens are generated out-of-band (e.g. `openssl rand -hex 32`) and handed to the user via a side channel.
- An invite is consumed exactly once: on the first successful enrollment for that userId. After consumption — or once the seeded pod has any credential on file — the invite flow refuses, so even a restarted container cannot replay the bootstrap.
- The seeded pod is read only once the invite matches the one configured for that userId, and only for a userId shaped like an account id (lowercase letters, digits and hyphens); that read writes nothing, and a pod that cannot be read is a `503`. A wrong invite gets `401` and touches no pod: the same `401` as a seeded account that already has a credential, and, on `/auth/siwe` and `/auth/did`, as an invite already spent. `/auth/webauthn/register-options` answers an invite spent in this process with `409` ("already been consumed"), which only the right invite reaches. `/auth/siwe` and `/auth/did` used to read the named pod first, which writes an empty `auth-methods.jsonld` when there is none, so anyone could plant a document in the pod of an account not opened yet (`x/../<id>` reaches any pod). `/auth/webauthn/register-options` read it only with the right invite, but wrote that empty document too, before any ceremony ran, and left it when the ceremony was abandoned. An account is also always the pod its document was read from, whatever the document's own `userId` says, so such a document no longer loads that account under another id.
- Not setting `BOOTSTRAP_INVITES` simply means no seeded legacy users can be first-enrolled. New users go straight to `u-pk-…` / `u-eth-…` / `u-did-…` derived identities.

### Self-audit endpoint

```
GET /auth-methods/me
Authorization: Bearer <identity-token>
```

Returns the full `auth-methods.jsonld` doc for the token's user — wallet addresses, WebAuthn credential IDs + `createdAt` + transports, DID keys + `createdAt`. Public-key bytes and WebAuthn counters are intentionally omitted (they're in the pod already and not useful for audit). Use this to verify no foreign credentials have accreted to your account (historical risk under the pre-fix userId-claim hijack).

### Per-surface agent detection (relay side)

The MCP relay mints per-user agents of the form `<surface>-<userId>` on the user's pod. The `<surface>` slug is derived automatically at OAuth completion time from the DCR-registered `client_name`:

| OAuth `client_name` pattern | Surface slug |
|---|---|
| `Claude Code (VS Code)` / `VSCode` | `claude-code-vscode` |
| `Claude Code` | `claude-code` |
| `Claude Desktop` / Mac / Windows | `claude-desktop` |
| `Claude Mobile` / iOS / Android | `claude-mobile` |
| `Claude` (anything else) | `claude` |
| `ChatGPT` | `chatgpt` |
| `OpenAI Codex` | `openai-codex` |
| bare `Codex` | `codex` |
| `Cursor`, `Windsurf`, `Cline`, `Zed`, `Continue` | their own slug |
| otherwise slugifiable (matches `^[a-z][a-z0-9-]{1,31}$`) | that slug |
| missing / unslugifiable | `RELAY_DEFAULT_SURFACE_AGENT` (default `mcp-client`) |

Two relay env vars control the fallback:

- `RELAY_DEFAULT_SURFACE_AGENT` (default `mcp-client`) — used when the OAuth `client_name` is missing or unrecognised. **Deliberately NOT `claude-*`** so an unknown client doesn't silently masquerade as Claude.
- `RELAY_SURFACE_AGENT` — legacy alias, kept so old deployments keep working.

A deployment that always serves a single surface (e.g. a dedicated mobile-only relay) can set `RELAY_DEFAULT_SURFACE_AGENT=claude-mobile` to pin the label.

**Surface agents are restored on demand.** The identity server keeps surface agents only in memory, and its boot-time rebuild brings back one placeholder agent per user. When `GET /agents/<id>/did.json` or `/agents/<id>/profile` finds no agent and the id is exactly `<surface>-<userId>`, with a relay-shaped slug and the canonical id (`u-pk-`, `u-eth-` or `u-did-` and 12 hex) of a user the server knows, it restores that user's agent with the name `ensureSurfaceAgent` would give it (`surface-agent-restore.ts`), but only if the user's pod agent registry (`<pod>/agents`, which the relay writes on OAuth) lists it, and with the scope that entry lists; a verified token for that agent, issued to that user, restores it too, with the scope the token was signed with. A restored agent is never broader than it was: an unknown or missing scope, or two entries that disagree, restore as `DiscoverOnly`. So a lookup cannot invent an agent the person never had, and made-up slugs cannot use up the person's restores (capped at 32 per user; past that a token brings an agent back). Unknown, deleted or non-canonical users, ambiguous ids and ids matching the janitor's `TEST_AGENT_PATTERN` are never restored. Because the id is what names the owner, `POST /register-agent` accepts only a plain lowercase slug (400 otherwise) and refuses with 403 an id ending in another user's canonical id, so nobody can register `claude-<victim>` and appear as its controller; the caller's own `<surface>-<their userId>` still registers, and a token naming another user's id does not verify.

**Deleting an account leaves a tombstone.** `POST /users/me/delete` cannot empty the pod: the container and its other files stay, and the relay maps a userId straight to that container. A derived id comes back from the credential it was derived from, and passkey ids are not secret, so the account's `auth-methods.jsonld` is overwritten with a tombstone rather than removed: the userId, the day (`deletedAt`) and a session epoch above every token issued, and no name, agent or credential. Every first sign-in reads that file before creating an account, so an old passkey id, wallet, DID or bootstrap invite gets 409 "This account was deleted", nothing is written, and the account's tokens are refused, after a restart too; a pod that cannot be read gives 503. The deletion itself is a 503 that changes nothing when the pod does not take the tombstone. When the pod may have taken it without saying so (a `5xx` after applying it, a timeout), the record is settled under the lock (a write the pod never answered is fenced first, so a deletion answered "Nothing was changed" cannot land afterwards), and a tombstone there completes the deletion (`200`, with the account's memory and agent registry cleared). If settling fails, the `503` says the deletion may have taken, and a retry with the same token finishes it (a retry, or a first deletion, whose read of the record fails sends nothing and answers `503` "Could not read this account just now", saying an earlier deletion may already have taken; it used to say the pod did not take the deletion): the token is refused everywhere else ("Account deleted"), but `POST /users/me/delete` accepts it while this process still holds the account, and writes nothing over a tombstone already there. `u-try-*` ids are random and keep the old removal. The tombstone is permanent: no sign-in lifts it, and an operator re-opens an id by editing it, not by deleting it (see *Re-opening a deleted id by hand*, below). Every writer of an existing account's record reads it from the pod under the same per-userId lock as the deletion, so it runs wholly before the tombstone (which is then written over its result) or after it, and once the tombstone is on the pod every write of that id but the tombstone is refused (a process-local set of deleted ids): nothing read before the deletion can be put back over it and re-open the account and its old tokens. That holds when a record without credentials is put back over the tombstone by hand, too: until the process restarts, a first sign-in to that id writes nothing and answers `409` ("This account was deleted and cannot be re-opened"). The tombstone's epoch is above both the pod's and this server's copy's. A passkey sign-in that found the account before its deletion and verifies against what this server held then gets 409. A `u-try-*` record is removed only if it is still the record read (`If-Match`); a claimed one (with a credential) whose removal fails stays whole, and the deletion is a 503. The janitor reaps a `u-try-*` account only if its record, read again under the lock, still holds no credential, and purges a Play owner only after writing its anchor back on the ETag it checked (a fence): an enrolment that lands first (the other instance's) makes that write fail, and the account is kept whole, while one that reads the anchor afterwards finds it expired, which no writer accepts. The same set keeps the account out of memory: `verifyToken` refuses a deleted id's tokens before reading anything, loading an account from its pod (at startup, on retry, on demand) skips a tombstone or a deleted id, so a read that began before the deletion cannot put the old record back, and an add-device ceremony begun before the deletion gets 409 without seeding the account's shell. That guarantee is per process; a second replica writing the same pod is not covered.

**Accounts deleted before tombstones are refused when they come back.** Until 2026-10-26 a deletion removed `auth-methods.jsonld` and `<pod>/agents` and kept everything else (the container, the relay's `profile/card` and `.acl` files, the descriptors under `context-graphs/` and the `.well-known/context-graphs` manifest, the inbox), so such a pod has no tombstone, and a derived id signing in to it again was created over it and inherited its files, its inbox, its did:web name and the envelopes encrypted to its agents. So before a first sign-in creates a derived id (`u-pk-`, `u-eth-` or `u-did-` and 12 hex, derived from the credential presented, never a bootstrap invite's seeded id), it asks the pod with HEAD requests whether a deleted account used it (`deletedBeforeTombstones` in `server.ts`, through the `vacated` hook in `first-sign-in.ts`). For `u-pk-`, any existing container counts: an owner's authenticator never presents the same credential id twice (every registration makes a new one), so no owner is turned away. For `u-eth-` and `u-did-`, the pod counts as deleted when `agents` is gone (only a deletion removes it) and the relay's `profile/card` is there. The relay writes that card only when it creates the pod's `agents` registry (its first touch of a pod, after this server issued a token for that very id), and only since 2026-06-04, so the card shows that an account here used the pod; a missing card shows nothing (see *What it cannot see*, later in this paragraph). Nothing else in the pod shows it: every `publish()` writes the `.well-known/context-graphs` manifest and files under `context-graphs/` (or wherever it is told), and a bridge holding the gate's write secret publishes into a signer's own `u-eth-` pod with no account here at all (a vertical's self-enrolment, credential issuance, ontology publishing). Counting the manifest or descriptors refused such a wallet's first sign-in as deleted and tombstoned it for good, so they do not count. A pod that kept `agents` lost only its sign-in record and stays its wallet's or key's, and the inbox is ignored, because anyone can deliver to a pod. A pod judged deleted gets 409 "This account was deleted", a `WARN identity_deleted_before_tombstone userId=… evidence=…` log line, and its tombstone, written under the account's lock and conditionally on the claim's own read, the state the probes judged (`If-None-Match: *` where it found no record, `If-Match` on its ETag where it found one), so a record another writer made or changed since is never replaced: the write is refused, the record the pod holds then is installed (a credential on it reaches the sign-in indexes), and the next sign-in asks again. What is written is installed only once the pod has it (see [Writes to auth-methods.jsonld](#writes-to-auth-methodsjsonld)); so the next attempt reads the tombstone and probes nothing. A probe the pod cannot answer is 503 and nothing is written; the probes are made under the same lock and give up after 15 s, like the record's own reads. The probe never runs for a record that lists credentials, a tombstone, or a credential that may not create an account (a did:web, an `existingOnly` sign-in, or any sign-in while accounts are loading), and a brand-new account pays one HEAD on its pod root (a `u-eth-`/`u-did-` pod that exists, three). What it cannot see: a deletion whose `auth-methods` DELETE failed (or that a race wrote back) is a live account again; a `u-eth-`/`u-did-` pod whose `agents` DELETE failed, or was re-created by the relay, or that has no card, can still be re-opened by its wallet or key (or by someone who finds a 48-bit collision); an account already re-opened is left alone; and a seeded id deleted before tombstones can be claimed again with its invite after a restart, so the operator removes the invite or writes the tombstone by hand. Pods without a card are more than the deletion date suggests. The relay wrote `<pod>/agents` (from its publish path and from `/oauth/verify`) long before it wrote any card, and it writes the card only when it creates `agents`, never later, and nothing has filled cards in since. So a `u-eth-`/`u-did-` pod whose `agents` registry was written before 2026-06-04 (such ids are derived since 2026-04-19) never got a card, however long its account used the relay after that and whenever before 2026-10-26 it was deleted; neither did a pod that never connected through the relay, whatever it published. The probe cannot tell such a pod, once deleted, from one a bridge published into, so it opens again. An operator finds these pods by looking at them: `tools/css-pod-evidence.mjs` (read-only) records, for each pod, whether it holds `auth-methods.jsonld`, `agents`, `profile/` and `credentials/`, and how many descriptors and inbox entries. A `u-eth-`/`u-did-` pod with neither `auth-methods.jsonld` nor `agents` that holds delegation credentials under `credentials/` (the relay's publish path wrote them with `agents`, and a deletion kept them), or that a retained `Deleted user <id>` log line names, is most likely a deleted account's; once the operator is satisfied it is, they write its tombstone by hand: the document a deletion writes, with `deletedAt`, `sessionEpoch` 1 and no credential. The probe does not count `credentials/`: the relay and the stdio MCP server write it next to `agents` as separate requests, so a registry write that failed while the credential's landed leaves the same shape on a pod nobody deleted, and `/oauth/verify` wrote `agents` without it, so counting it would refuse some live wallets for good and still miss some deleted pods. Whom it can refuse wrongly: no passkey owner (none can present the same credential id again), and only a wallet or key whose first sign-in record was lost on a pod where the relay wrote the card and never `agents`; the log line names each.

**Re-opening a deleted id by hand.** An operator re-opens a deleted id by editing its tombstone into a record that lists the credential to admit: remove `deletedAt`, keep `sessionEpoch` (so every token issued before the deletion stays refused), and add the wallet address, the did:key with its key, or the passkey's credential record as it was before the deletion (the tombstone kept none, so it comes from a backup; without one, the passkey's owner registers a new credential, which is a new id). Then restart the process, which keeps the ids it deleted, and what it last read of each record, in memory. A record that lists a credential is never probed. Editing is the only supported way to re-open an id; deleting the tombstone is not one. For a `u-pk-` id, and for a `u-eth-`/`u-did-` id whose pod has the relay's `profile/card`, deleting it does not re-open the id: the pod still looks the way a deletion leaves it, so the next first sign-in probes it, gets 409, writes the tombstone again and logs `identity_deleted_before_tombstone`. A `u-pk-` id stays refused while its container exists, and a `u-eth-`/`u-did-` id while `agents` is gone and `profile/card` is there. A `u-eth-`/`u-did-` pod without the card (its `agents` registry predates 2026-06-04, or it never connected through the relay; see *What it cannot see* in the paragraph above) shows nothing once its tombstone is gone, and neither does a carded pod once `agents` exists again or the card is gone: deleting the file and restarting re-opens the id to its wallet or key, over the old pod, with a new record at session epoch 0, so the deleted account's unexpired tokens verify again. A seeded id is never probed, so deleting its tombstone lets its invite claim it again, with the same loss of the epoch.

## Threat model: who reads and writes `auth-methods.jsonld`

The pod's CSS is allow-all behind the css-gate, and the record is plaintext, so the gate is what decides who touches it (`deploy/css-gate/server.mjs`).

- **Reads.** Every other pod document reads anonymously. This one is read like a write: the pod's owner (their bearer) or the operator. Before 2026-10-13 it was public too, and since the root container lists every pod, anyone could collect every account's display name with its wallet addresses, passkey ids, labels, public keys and counters, and DID keys. The identity server is unaffected: it reads the record from CSS over the private network, not through the gate. A user audits their own through `GET /auth-methods/me` (above).
- **Writes.** A user's bearer writes only into its own pod. The gate decides that on the path it forwards, after `.` and `..` segments are resolved. Before 2026-10-13 it decided on the raw request-target, so `PUT /alice/../bob/auth-methods.jsonld` with alice's bearer passed as a write to alice and reached CSS as a write to bob's sign-in record. A user bearer is also refused on a path with an encoded `/` or `\` in a segment, since whether CSS decodes it would decide the pod.
- **Writes to the sign-in record itself.** Only the operator bearer writes `auth-methods.jsonld` through the gate, along with its `.acl` and `.meta` resources and a POST whose `Slug` names it. The identity server is its only writer, and it writes over the private network, not through the gate: enrolment, passkey removal and account deletion all happen there. Until 2026-10-13 a user's bearer could write its own record. A stolen bearer, or an OAuth token a client holds, could then add the thief's own passkey, wallet or DID, and keep signing in after the bearer expired. A user changes credentials through the identity server's endpoints, which require a sign-in.

## Known-good tradeoffs, documented

**WebAuthn credentials are RP-bound** to the origin they were registered at (spec-mandated; passkeys are cryptographically scoped to an RP ID). If Interego ever moves to a new public URL, users re-enroll their passkey for the new origin. This is *not* a sovereignty loss — the user's DID, wallet, and did-key methods all remain portable across origins, and WebAuthn is explicitly positioned as one of several methods, not the canonical one. Users concerned about origin lock-in should enroll a DID or wallet method in addition to their passkey.

**Tokens are bearer tokens** by default (stolen token = usable token). DPoP (RFC 9449) is the standard mitigation — cryptographic proof-of-possession on every request. MCP spec lists DPoP as optional and most clients don't implement it yet, so we haven't forced it. When MCP client support matures, DPoP slots into this architecture with no other changes (add a per-request JWT signed by a client-held key, server verifies on `/mcp`).

**Pod durability** depends on CSS persistence. The identity server is provably stateless, but CSS itself runs in-memory by default on Azure Container Apps. Long-term durability requires configuring CSS with a persistent backend (file store on Azure Files volume, quadstore in Postgres, etc.). This is a deploy-level concern separate from the identity-layer architecture.

**Writes are acknowledged only once the pod has them, at the cost of latency.** An add with a bearer waits for one read and one write of the account's record (see [Writes to auth-methods.jsonld](#writes-to-auth-methodsjsonld)), where it used to answer before writing. Nothing acknowledged is lost to a crash or a failed write, and a write that fails is a refused request the user can retry. A 15 s write timeout can turn a slow write that succeeded into an error; the write is then settled (a read, and while the record has not moved, a fence that keeps the write from landing later, then a read), so this server agrees with the pod for good, and the retry changes nothing. When the pod is too slow for the settlement too, nothing settles it, and the `503` says the write may or may not have been saved.

## Extending

- **New verification method.** Implement a `/auth/<method>` endpoint that validates a signature over a text that names this server and carries a `/challenges`-issued nonce, resolves the user via the appropriate index (or first-time flow), and returns the standard token response. Add a corresponding card to the relay's authorize page with client-side ceremony JS.
- **External identity server.** Point the relay at a different `IDENTITY_URL`; the identity server is federation-friendly (DIDs + WebFinger are resolvable by any conforming client).
- **Decentralized identity proof (VC-style).** The DID method already hands you a signature over a challenge this server issued (its message, which names this server, or, while `DID_ACCEPT_BARE_NONCE` allows it, its bare nonce); layer a W3C Verifiable Credential on top for claims ("is over 18", "is a member of X") without centralized attestation.
