# Provisional browser owners (deployment composition)

This implementation lets an explicitly trusted application provision a browser-controlled native owner and pod on a Play action, then attach a normal credential or copy a confirmed checkpoint into an existing owner's pod. It is an implementation composition, not a change to the Interego protocol. A browser-key proof establishes possession of that key; it does not identify a human or authorize autonomous agents.

The feature is disabled unless `PROVISIONAL_PLAY_CLIENTS` explicitly maps each allowed HTTPS application origin to its existing native service agent DID and public owner-pod URL:

```json
{"https://play.example":{"agentDid":"did:web:identity.example:agents:game-service","podUrl":"https://pods.example/game/"}}
```

## More than one application

Each entry may also carry two optional fields:

```json
{"https://play.example":{"agentDid":"did:web:identity.example:agents:game-service","podUrl":"https://pods.example/game/"},
 "https://learn.example":{"agentDid":"did:web:identity.example:agents:learn-service","podUrl":"https://pods.example/learn/","namespace":"foxxi","maxPods":25}}
```

`namespace` is the application's slug, matching `^[a-z][a-z0-9-]{1,31}$`. It names the one directory and graph family that application's guests may write: the gate's `<pod>/<namespace>/checkpoints/<sha256('urn:graph:<namespace>:<kind>:<sha256(ownerDid)>')>.json` and the relay's `urn:graph:<namespace>:<kind>:<sha256(ownerDid)>`, for the same two kinds as before (`player-profile`, `player-profile-index`). An entry without one, or naming `hallowmarch`, is the first application: its guest token, paths and graphs are byte-identical to what they were. Names a guest pod already uses (`context-graphs`, `agents`, `profile`, `settings`, `inbox`, `play-budget`, `play-exchanges`, `play-exchange-limits`, `play-limits`, `auth-methods`) are refused, and a malformed value stops identity at start instead of being ignored. Two origins may share a namespace; their guests are still different owners with different pods, because the owner ID is derived from the origin.

The namespace is configuration, not a claim. It is not in the anchor and no request can supply it. Identity copies it from this map into the signed guest token marker (`provisionalPlay.namespace`) when the token is issued, only for a namespace other than `hallowmarch`, and a token whose marker does not match the namespace configured now for its owner's application does not verify (`Provisional owner binding mismatch`). Changing an application's namespace therefore ends that application's outstanding guest tokens. Do not change the namespace of an application that has live guests: a fresh grant gives the same owner a token for the new namespace, but a guest that already bound its graphs under the old one has spent its two bindings, and the relay refuses any under the new one (`409 provisional_namespace_changed`, before anything is written). Such a guest can save nothing further until its deadline, and what it wrote under the old namespace stays in the pod, unreachable to it, until the janitor's cleanup. A guest that had bound nothing yet continues under the new namespace. The relay and the gate read the namespace only from the marker identity verified. Each checks its shape again, refuses a credential whose namespace is present and malformed (it is never taken for the default), and treats an absent one as `hallowmarch`.

`maxPods` (1 to 1000) is that application's own lifetime admission cap. It is counted over the admission ledger's entries whose attestation names the application's origin, expired guests included, so the ledger's format is unchanged and nothing is migrated. `PROVISIONAL_PLAY_MAX_PODS` still bounds the total across all applications and is checked first: an application's cap can only narrow its share. Reaching it answers `503 provisional_play_application_capacity`; reaching the total answers `503 provisional_play_lifetime_capacity`, as before. An application without `maxPods` is bounded by the total alone, so give each application a cap when one must not be able to use up another's admissions. A ledger entry that no longer opens (signed under a key since replaced) counts toward the total only.

**Rollout order.** The three services deploy independently, and each step is safe on its own as long as a namespace is configured last:

1. Deploy the relay and the gate with this change. Without a namespace in any marker they behave exactly as before.
2. Deploy identity with this change. Until an entry names a namespace, every marker is still the old three-field one.
3. Only then add `namespace` (and `maxPods`) to `PROVISIONAL_PLAY_CLIENTS`.

A relay or gate from before this change ignores the field and applies the first application's surface: an old gate would let a second application's guest write the two `hallowmarch/checkpoints/` documents of its own pod (still its own pod, its own budget, the same bounds), and an old relay would refuse that guest's graphs. Neither crosses to another owner, but neither is the intended surface, hence step 3 last. The cleanup needs no ordering: it recognises saves under any well-formed namespace.

A second application also needs its origin in `PROVISIONAL_PLAY_CLIENTS` (which adds it to identity's CORS allowlist), its own native service agent and pod, and browser code that holds the non-extractable P-256 key and requests grants. What its own backend accepts from a guest is that application's decision; nothing here grants a guest anything beyond the two checkpoint documents and the relay tools listed below.

**Foxxi.** Foxxi is not configured as an application here by default. Its bridge can issue grants and its dashboard can keep a guest in a provisional pod once an operator turns that on (`applications/foxxi-content-intelligence/DURABLE-GUEST.md`); nothing in this document changes for it. Its dashboard's "Start as a guest" makes a secp256k1 wallet in the tab (`applications/foxxi-content-intelligence/dashboard-app/src/auth/session.ts`, `connectAsGuest`) and signs each request to the Foxxi bridge with it, as `did:ethr:<address>`. It calls neither identity nor the relay: no identity account, no pod, no guest deadline, no admission budget, and the key is gone with the tab unless the guest wrote down its recovery phrase. (This paragraph first said the wallet signed in through SIWE and created a `u-eth-` account. It does not.) A provisional guest is the opposite trade: a `u-try-play-` owner with a fixed deadline, a lifetime admission cap, two bounded encrypted documents, and a key that survives a reload (IndexedDB) and can later be claimed with a passkey or wallet. Foxxi's I2IDL-X learner sign-in through the relay still refuses any account that carries the provisional marker (`applications/foxxi-content-intelligence/src/i2idlx-learning-auth.ts`): a kept guest is a dashboard guest. Separately, the I2IDL-X workbench can admit a provisional guest to its learner operations only, by the other door this provider offers: the guest's browser key signs a workbench challenge and the workbench asks `/play/provisional/verify`. The workbench is a second application, with its own origin, service account and entry in `PROVISIONAL_PLAY_CLIENTS`, and is off unless the bridge is given that service's key (`applications/foxxi-content-intelligence/i2idlx/LEARNING-CONNECTIONS.md`, "Guest learners"). Those routes write nothing to the guest's pod.

## General guest

A per-application guest is one owner per application: its key lives in the application's origin, and its id is derived from that origin. A **general guest** is one owner per browser across every application that offers it. It is off unless identity is started with `PROVISIONAL_GENERAL_GUEST=1` (exactly `1`), and an application takes part only when its entry in `PROVISIONAL_PLAY_CLIENTS` says so:

```json
{"https://play.example":{"agentDid":"did:web:identity.example:agents:game-service","podUrl":"https://pods.example/game/",
  "generalGuest":true,"generalGuestReturnPath":"/guest/return"}}
```

`generalGuestReturnPath` is the one path on that origin the door sends a browser back to: absolute, plain segments, no query or fragment, at most 128 characters. `"generalGuest": true` without a valid one stops identity at start. With the setting off these fields are read and ignored: there is no door, no exchange, the metadata at `/.well-known/play-provisional` has no `generalGuest` member, a per-application guest's id, token, paths and record are what they were, and the door's four paths answer as any path that never existed (`provisional-general-guest-routes.test.ts` compares them with one). An identity from before this change ignores both fields.

**What is the same.** The anchor, the admission ledger with its deployment and per-application caps, the fixed deadline (`PROVISIONAL_PLAY_TTL_SECONDS`), the hosted-terms gate, the 16 live grant receipts, the claim with a passkey, wallet or DID, the janitor and the cleanup are the per-application guest's, through the same code. The first application to send a browser pays the admission from its own `maxPods` and from the total; an application the same guest reaches later pays nothing. The ledger entry's attestation names the application that paid.

**What is different.**

- The owner id is `u-try-guest-<32 hex>`, the first 32 hex characters of `sha256("interego-general-guest-v1\n" + thumbprint)`: a function of the key alone. A per-application guest's is `u-try-play-…`, derived from the application origin and the key, so the same key is two different owners and the two kinds never collide. The anchor carries `general: true`, and neither kind's anchor opens as the other's.
- The key lives on identity's origin. `GET /guest/door` is a page that creates a non-extractable P-256 key in identity-origin IndexedDB (`interego-general-guest`) and signs with it. It is a top-level document only (`frame-ancestors 'none'`, `X-Frame-Options: DENY`), runs one inline script named by hash in its Content-Security-Policy, connects to this origin alone, and proceeds only on a click.
- Each application that sends the browser is recorded on the owner's record (`provisionalGuestApplications`), and that list is one of the guest's attributes.

### The door and the exchange

1. The application's backend makes a `state` (20 to 128 base64url characters) and a PKCE verifier it keeps, and has its service agent sign, through the relay's `sign_request` as for a per-application grant:

   ```json
   {"purpose":"interego-general-guest-v1","audience":"https://play.example","state":"<state>","codeChallenge":"<base64url sha256 of the verifier>","expiresAt":1800000060}
   ```

   The relay adds `agent_id`, `subject_pod_url` and `timestamp`. The purpose differs from a per-application grant's, so neither is accepted in the other's place. `applications/_shared/guest-access/door.ts` (`GeneralGuestDoor`) does this step and the last, and `PlayGrantService.generalGuestGrant` signs.
2. It sends the browser, by a top-level navigation, to `<identity>/guest/door#grant=<base64url(JSON {_signed_payload,_signature})>`. The grant is in the fragment: identity's server and its logs never see it in a request line, and the page removes it from the address at once.
3. The page shows the application's origin and waits for a click. It then signs these bytes with the browser's key and posts `{playGrant, publicKeyJwk, proof, termsVersion?}` to `POST /guest/door`:

   ```text
   interego-general-guest-door-v1
   {playGrant._signed_payload}
   {playGrant._signature}
   ```

   (with `\nHosted-Interego-Terms: <version>` appended where terms are active). Identity answers only a request whose `Origin` is its own. It verifies the grant as it verifies a per-application one (the configured principal and pod, through the configured relay), admits the key's guest or finds it, records the application, and answers `{redirect}`: the application's origin, its registered return path, `?code=…&state=…`. The address is built from configuration; nothing in the request names it. The page navigates there only if its origin is the grant's audience.
4. The application's backend posts `{code, codeVerifier, audience, state}` to `POST /guest/exchange`. The code lives 60 seconds, is signed by identity, names its audience and state, and is spent on the owner's record by a conditional write, so it is used once on every instance (`guest_code_already_used` after that). The verifier must hash to the challenge the application's service agent signed. The answer is `valid:true`, `provisional:true`, `general:true`, the issuer and audience, `userId`, `ownerDid`, `webId`, public `podUrl`, the default agent's id and DID, `proofKeyThumbprint`, ISO `guestExpiresAt`, the application's `namespace`, `guestAttributes`, and `token` with `tokenExpiresAt`. It does not include the anchor: no application ever holds a general guest's attestation, and `POST /play/provisional/verify` answers none (`invalid_attestation`).

An application must bind a visit to the browser that started it (an HttpOnly cookie set when it redirects to the door, checked on return), or a return address carrying someone else's code and state would sign a visitor in as that someone. `GeneralGuestDoor` requires that binding.

### Attributes

`guestAttributes` is what identity holds about the guest, read from the owner's record on the pod, never from a request or from the token:

```json
{"subject":"did:web:identity.example:users:u-try-guest-…","provisional":true,"claimed":false,"createdAt":1800000000,"expiresAt":1800086400,
 "admittedBy":["https://play.example","https://learn.example"],"proofKeyThumbprint":"…","hostedTermsVersion":"2026-11-06-r2"}
```

`claimed` is true once the record lists a passkey, wallet or DID. Times are Unix seconds. It is published in the exchange answer and, for a general guest's token, in `POST /tokens/verify` beside `provisionalPlay`. Neither answer is signed separately: both are identity's own HTTPS answers, authoritative as introspection already is.

### Tokens

A general guest's token carries `provisionalPlay` **without an `audience`**:

- an application token: `{general:true, application:"https://play.example", proofKeyThumbprint, expiresAt, namespace?}`. Identity answers it on `POST /tokens/verify` only, while the application is still opted in, is on the guest's record, and its namespace is the one the token carries. Every other route of identity refuses it (401): it cannot read `/me`, renew itself, register an agent, enrol a credential, sign out or delete the account. An application that needs a fresh one sends the browser through the door again.
- a door token: `{general:true, door:true, proofKeyThumbprint, expiresAt}`, answered only to the door page by `POST /guest/door/claim` after the key signs `interego-general-guest-claim-v1\n{issuer}\n{thumbprint}\n{expiresAt}` (`expiresAt` within 120 s; each proof is used once). It is the guest's bearer for the existing claim flow: the page opens `/connect?claim=<token>` on identity's own origin, and what follows is the add-device flow described below. `<identity>/guest/door#claim` is the address an application links to for it. The css-gate grants a door token no write.

### Policy at the css-gate

What a general guest may write is decided by policy over its attributes, not by a branch for it. The gate reads `guestAttributes` from identity's introspection answer, builds the guest's attribute graph, and evaluates the standard policy set of the token's application (`deploy/css-gate/guest-access.mjs`, a byte-identical copy of `applications/_shared/guest-access/guest-access.mjs`): a provisional guest that this application admitted, whose deadline has not passed, may `guest:WriteCheckpoint`; a guest past its deadline is denied by an explicit Deny; everything else is refused, because the decision is default-deny (no applicable Permit is a refusal, as is a missing or malformed attribute). The attributes must be the token's own (same owner, key and deadline). Once the policy permits, the write is held to the per-application surface's shape by the same code: the two documents `<pod>/<namespace>/checkpoints/<sha256('urn:graph:<namespace>:<kind>:<sha256(ownerDid)>')>.json`, a conditional native commit, 4 MiB per write. The lifetime budget (`play-budget.json`, 32 MiB and 1024 attempts) is one per pod, shared by every application that writes to it. A per-application guest's check is unchanged and does not go through the policy. The gate also refuses a general guest's token any read of the pod's private documents (`auth-methods.jsonld`, `play-budget.json`): the record lists the owner's credentials and the other applications it has used, and an application learns of those only what identity states in `guestAttributes`.

The policies are `iep:AccessControlPolicy`-shaped records with the mini-SHACL predicate shapes `@interego/abac` evaluates, and the helper's evaluator is a port of that package's `evaluate` with no imports, so the gate's image can carry it; `applications/_shared/tests/guest-access.test.ts` holds the two to the same verdicts on the same policies and graphs. The attribute and action names (`guest:provisional`, `guest:admittedBy`, `guest:secondsRemaining`, `guest:WriteCheckpoint`, …) are a deployment vocabulary declared in `applications/_shared/guest-access/ontology/guest.ttl`, not protocol terms. The relay offers a general guest nothing: its parser refuses the marker.

### Linkability

A general guest is linkable across applications by design. Every application the browser enters through the door learns the same owner DID, WebID, pod URL and key thumbprint, when the guest was created and when it ends, whether it has been claimed, and the origins of the other applications it has used (`admittedBy`). Two applications can therefore tell they are serving the same browser, and each can see which others it has visited. Pod reads are not gated by the css-gate, so what an application writes to the pod is as readable as any pod content; the checkpoint documents must be owner-encrypted envelopes. A visitor who does not want that link uses an application's own guest door, which is unchanged. The door page says this before the click.

### Rollout order and mixed versions

The three services deploy independently. Every combination is safe, because each service from before this change refuses a general guest's token outright:

| Service version | What it does with a general guest's token |
| --- | --- |
| css-gate before this change | `verifiedProvisional` requires `provisionalPlay.audience` to parse as an https origin and the owner id to match `^u-try-play-[a-f0-9]{32}$`. Neither holds: `401 provisional_play_invalid`. It never becomes ordinary ownership, because the marker is present. |
| relay before this change | `parseProvisionalPlay` requires a non-empty string `audience`: `invalid_provisional_authority`, and the bearer is not authenticated. The relay's own guest exchange also needs `/me` and `/play/provisional/verify`, which identity refuses for this token and this guest. |
| identity before this change (a rollback) | The owner's anchor does not open (its id is not the per-application derivation): `Provisional owner unavailable`. Its janitor treats `u-try-guest-…` as an evaluation account and removes an unclaimed one after `TRY_USER_TTL_MS` through the ordinary deletion, which leaves game data the native delete would have removed until an identity with this change runs its backfill. |
| identity with this change, setting off | No door. A general guest's anchor opens for the cleanup alone, so its tokens are refused and the janitor still removes it at its deadline. |

So the order is:

1. Deploy the css-gate and the relay with this change. Without a general token in circulation they behave as before.
2. Deploy identity with this change, the setting still off.
3. Add `generalGuest` and `generalGuestReturnPath` to the applications that want it, deploy those applications with their return path, and only then set `PROVISIONAL_GENERAL_GUEST=1`.

Turning the setting off again ends every general guest's tokens at once and removes the door; their pods are cleaned up at their deadlines as usual. A css-gate with this change in front of an identity without it sees no general token and no `guestAttributes`, and changes nothing.

**Applications.** The coached world offers the door beside its own when `CPW_GENERAL_GUEST=1` (with its relay door configured; return path `/play/general/return`). Foxxi's bridge can sign door grants (`PlayGrantService.generalGuestGrant`) but its learner workbench does not use the door yet: its guest sessions are re-checked with identity while they live, and an application token cannot be re-checked by the application.

## Configuration and protocol

Identity also needs its existing stable `TOKEN_SIGNING_KEY`, `CSS_URL`, `RELAY_URL`, and canonical HTTPS `CSS_PUBLIC_URL`. The allowlisted application origins are added to identity's existing explicit CORS allowlist. No wildcard or shared Play secret is introduced.

`GET /.well-known/play-provisional` advertises the enabled state, endpoints, proof encoding, lifetime admission limit, guest deadline and storage limits. `PROVISIONAL_PLAY_TTL_SECONDS` defaults to 86400 and is bounded to 3600–604800. `PROVISIONAL_PLAY_MAX_PODS` defaults to 100 and is bounded to 1–1000. This limit is both a live-pod limit and a **cumulative lifetime admission limit**. Raising it is an explicit operator storage-budget decision.

The application first obtains a native `sign_request` envelope using its existing service credential. Its payload is:

```json
{"purpose":"interego-play-provisional-v1","audience":"https://play.example","publicKeyThumbprint":"<RFC7638 P-256 thumbprint>","challenge":"<20–128 base64url characters>","expiresAt":1800000060}
```

The relay adds the authenticated `agent_id`, public `subject_pod_url`, and ISO timestamp. Once the relay's operator turns it on (`RELAY_SIGN_CLIENT_ID=1`), it may also add `client_id`, the OAuth client its session's access token was issued to; it is absent when the envelope was not asked for over an OAuth session. Identity does not read it and does not refuse it. The grant expires within 120 seconds of that timestamp. Identity verifies the exact configured principal and pod through the fixed configured relay's `verify_agent`, including its live signing anchor and delegation, then recovers the signature over the relay's `sha256:<hex>` message. Caller-supplied URLs never select a verification server.

The browser stores a nonextractable P-256 private `CryptoKey` in IndexedDB and posts `{playGrant, publicKeyJwk, proof}` to `/play/provisional`. `playGrant` is `{_signed_payload,_signature}`. The signature uses WebCrypto ECDSA P-256/SHA-256 over these UTF-8 bytes, with actual newline separators:

```text
interego-play-provisional-v1
{playGrant._signed_payload}
{playGrant._signature}
```

The base64url proof encodes the raw 64-byte `r || s` signature. The public JWK has only public P-256 material; a JWK containing `d` is refused. The RFC7638 thumbprint hashes `JSON.stringify({crv:'P-256',kty:'EC',x,y})` with SHA-256.

If hosted enrollment terms are active, the metadata includes `terms` with the version, Terms URL and Privacy Notice URL. Creation without agreement returns `428 hosted_terms_required` with those links before an admission is reserved. After the player agrees, include `termsVersion` in the bootstrap request and append `\nHosted-Interego-Terms: <version>` to the signed proof bytes. A fresh grant after the agreement allows time to read the Terms. Existing guests can use the original proof to resume.

Success returns the existing identity credential fields (`token`, ISO `expiresAt`, `userId`, `did`, `webId`, `agentId`, `agentDid`, public `podUrl`) plus `attestation`, `provisional:true`, fixed ISO `guestExpiresAt` and `proofKeyThumbprint`. The native identity token stays between browser and identity/relay. The relay's separate provisional exchange creates the normal durable OAuth credential required by `/mcp`; a `cg2_` identity token alone is not an MCP OAuth credential.

The native guest owner ID is derived from application audience and public-key thumbprint. A fresh grant for that same key resumes the same owner, pod and original deadline. A grant hash is consumed in the canonical pod anchor before issuing any credential; replay returns `play_grant_already_used`. A lost response can be recovered with a fresh application grant and new key proof. At most 16 live 120-second receipts are retained.

The root control resource `<CSS_URL>provisional-play-admission.json` reserves each owner before creating its pod. Its conditional writes persist up to the configured lifetime limit of immutable original attestations. Expiring or deleting a pod never refunds an admission, and a restart cannot reset the budget. This lifetime count also bounds active Play pods, so admission does not enumerate the CSS root. An interrupted creation can reuse its reservation without extending its original deadline. Failure to read or conditionally persist either admission or the own-pod `auth-methods.jsonld` anchor prevents credential issuance. This control ledger contains no character checkpoint or private key.

For game admission or a later claim, the browser signs a fresh application challenge over:

```text
interego-play-proof-v1
{attestation}
{audience}
{challenge}
```

`POST /play/provisional/verify` accepts `{attestation,audience,challenge,proof}`. It verifies the provider signature, browser proof, original expiry, and exact live pod anchor. Success includes `valid:true`, `provisional:true`, issuer/audience, canonical owner DID/WebID/public pod, actual default authenticated agent ID/DID, public key/thumbprint, ISO expiry, and `['human-play','own-pod-checkpoint']`. The application owns one-time challenge consumption and binds claim challenges to the independently verified canonical target. The attestation is public proof material, not a bearer credential.

Guest identity tokens carry signed `provisionalPlay:{audience,proofKeyThumbprint,expiresAt}` (Unix seconds), plus `namespace` for an application that configures one other than `hallowmarch` (see "More than one application"). Introspection and `/me` expose it with authoritative canonical owner/pod/agent fields. Renewal preserves the marker and deadline, and is issued at the session epoch of the owner's record as the presented token's check read it from the pod (that check never decides the token's validity or epoch on the identity server's copy, which can be behind the pod, and a renewal issued at the copy's epoch was refused everywhere). The token cannot register an additional identity agent. Relay and CSS gate enforce the marker's restricted checkpoint surface: two deterministic resources, conditional native writes, 4 MiB per write, 32 MiB lifetime decoded writes and 1024 lifetime attempts. These limits require the matching relay and gate rollout before enabling an application audience.

An explicit new passkey/wallet/DID enrollment can use the existing add-device flow to claim the same owner/pod. When the owner's anchor cannot be read at that moment, an enrollment with the guest bearer (a wallet or DID through `/auth/siwe`, `/auth/did` or `/wallet/link`, or a passkey's registration options), and any other request that acts on the owner's account with it, answers 503 (try again) and changes nothing; an anchor that does not open to the owner is a 401. A guest's `POST /users/me/delete` overwrites the owner's anchor with a deletion tombstone, conditionally on the record it read, and never removes it: a write still pending from before (an add the pod never answered) is conditional on that record's ETag, and Community Solid Server 7.2 applies such a write to a missing document, so a removed anchor let it re-create the owner with its credential, the guest token verifying again at once. A deletion whose tombstone the pod refuses answers 503 and keeps the owner, its guest token still working. A fresh grant for the same key provisions the owner again over its tombstone (written on the tombstone's ETag, keeping its session epoch, so the tokens issued before the deletion stay refused), with its original deadline. A guest token's session epoch is checked on the owner's record as read from the pod, on every instance, so a token issued before the deletion is refused there and the new session's tokens verify, even on an instance whose copy of the record is still the tombstone. The guest token's check that makes that copy the tombstone leaves it stale, so when the owner, provisioned again, is claimed with a passkey, wallet or DID through another instance, that credential's tokens are the owner's on this one at once: they verify, and their deletion deletes (for up to 10 s they were "Account deleted" there, and their deletion was answered 409). A retry of a deletion answered 503 writes nothing over an owner provisioned again (401). A successful normal credential proof produces a canonical unmarked credential; merely renewing a guest bearer does not. The original guest attestation remains a valid source proof until its original expiry so same-owner claim confirmation can finish. Claiming into an existing owner remains an explicit browser copy-and-confirm operation with a conflict when a target character already exists; this provider does not alias owners or overwrite characters.

The existing janitor recognizes the signed fixed guest deadline after restart, rereads credentials before removal, and exempts a claimed pod. Play cleanup validates the complete own-pod tree first, then closes the owner (its tombstone written on the ETag of the record it checked: an enrolment that landed first keeps the whole pod), and only then deletes at most 128 descendants across eight levels; the auth record, now the tombstone, and the pod's container stay, for the reason above. A dependency failure or foreign/out-of-bounds traversal before the close retains the pod for a later retry. One after it (a deletion that fails) leaves the owner closed with its tombstone marked as a purge not yet finished (`provisionalPlayPurgePending`, cleared once every descendant is deleted but those below): the janitor's next pass sends the remaining deletions again, and so does its first pass after a restart, whose scan finds the mark. The guest's game saves (`<namespace>/checkpoints/<64 lowercase hex>.json`, for any well-formed application namespace that is not a name a guest pod uses for something else, `hallowmarch` among them, whether or not it is configured now: an application removed from `PROVISIONAL_PLAY_CLIENTS` before its guests are cleaned up does not leave their saves on the store) and its write budget (`play-budget.json`), which the gate writes only as native commits and the production store refuses to remove with a plain `DELETE` (`409`), are deleted with the store's native conditional delete. Only those two paths, relative to the pod root, are ever sent one (the cleanup refuses the anchor and the pod root a second time on its own), and only after the owner has been closed for the purge. It is sent only where the store advertises it (`Interego-Native-Delete: 1` on `OPTIONS`), to the store at `CSS_URL`, not through the gate: the cleanup reads the document's strong ETag with a `HEAD` (a `404` there is a document already gone) and sends `DELETE` with `Interego-Native-Delete: 1` and `If-Match` on that ETag, which deletes that exact revision (`205`). A store that does not advertise it, a `412` (the document changed or went since its ETag was read), a `409` (a document there that is not a native head) or any other answer leaves the purge unfinished for the next pass, which lists the pod and reads the document again. After a `412` that pass deletes the new revision. A document at one of those paths that is not a native head is answered `409` at every pass instead, and holds the purge open until someone removes it (the cleanup never sends it a plain `DELETE`); the gate writes those paths only as native commits, so it never leaves one there. The containers the game data emptied are deleted after it, with an ordinary `DELETE`. Once every deletion is done, the cleanup lists the pod once more: a write the gate authorized before the tombstone can still land after it, and game data found then leaves the purge unfinished too, for the next pass to delete (one that reaches the store only after that listing is not seen until the game-data backfill below). A document outside those two paths that the store refuses with `409` (a native head nothing expects) is kept, with the containers that hold it, and the purge finishes and logs it once: no plain request deletes it and the cleanup sends it no native delete, so a purge kept open for it would be sent again at every pass and after every restart without end. Until now the saves and the budget were kept that way too, so every guest's game data stayed on the pod after its purge; before that, their `409` counted as a failed deletion, and the purge of a guest who had saved never finished. At most one cleanup of an owner waits for its lock or runs at a time: a pass that starts while one is still running queues none of its own, and the first pass after it has returned takes the owner up again if its cleanup is still unfinished. A tombstone the cleanup did not mark (a guest's deletion, possibly made through another instance) is never purged: that owner may be provisioned again over it until its original deadline, so nothing of its pod is written or deleted (the cleanup lists the pod and reads the record before it finds the tombstone). The one exception is identity's game-data backfill, which deletes only game data left behind: by cleanups that finished before the native delete existed, and by a save that landed after a cleanup's last listing. Once per identity process, one janitor interval after it starts, it reads the admission ledger and takes each owner whose original deadline there passed over an hour ago, and that the process does not hold when it starts, through the cleanup again, one at a time (a turn that leaves an owner as it is leaves the janitor's queue as it was: a load may have queued the owner's unfinished cleanup meanwhile). It marks the tombstone again (on its ETag, under the owner's lock) only where the cleanup's listing names game data and nothing besides the pod root, the record, and an application namespace's two containers (`<namespace>/` and `<namespace>/checkpoints/`), the record is a tombstone dated no earlier than the deadline's day, and the store advertises its native delete; the cleanup then deletes the game data and those two containers and clears the mark. It never creates a record, writes the ledger, or touches an owner that holds a credential or whose deadline has not passed by the hour. A tombstone dated before the deadline's day is a guest's own deletion and is left as it is. Two kinds of pod are still included when they hold nothing but game data, because their tombstones look like a cleanup's: a guest's own deletion made on the day of its deadline, and an owner that claimed the pod with a credential and later deleted its account. In the process that re-opened a cleanup, a later pass deletes nothing while the pod holds anything more, and the cleanup stays marked; after a restart the startup scan finds the mark, and the cleanup is an ordinary one, which deletes everything listed but the record and the root. It stops at the first cleanup it takes up that does not finish, and when the store does not advertise the native delete, and logs an `ERROR` line for either; an `OPTIONS` answered `5xx` is no answer, and only that owner goes unchecked. Before it re-opens anything, it finishes, one at a time, the cleanup of each due owner that is unfinished (one an earlier start re-opened, whose mark the startup scan found), and re-opens nothing if one of them does not finish: a failure that repeats leaves one cleanup marked, not one more at every start. A guest's deletion this instance answered `503` (the pod may have taken it without confirming it) is left as it is for the guest's retry until that deadline; after it, the janitor finishes the deletion as the retry would have, sending the owner's agent registry a `DELETE` and nothing else. A `DELETE` the pod does not answer with a `2xx` or `404` leaves the deletion unfinished, and the janitor's next pass sends it again (it used to be logged as deleted whatever the answer, and never sent again). Deleting live resources, native heads included (the store's native delete removes the head and leaves its content-addressed nodes to garbage collection), does not assert that historical immutable PGSL atoms were physically reclaimed. The cumulative admission budget remains charged, and deleting the write budget gives the guest no new writes: its guest deadline has passed, after which the gate refuses every write and no grant provisions the owner again.

Validation: `npm run build --workspace @interego/identity` and `npm run test --workspace @interego/identity` from the monorepo after installing its dev dependencies. The tests use generated local keys and fake conditional storage only (the route tests' stand-in pod answers a plain `PUT` or `DELETE` of a native-committed resource with `409`, and the native conditional delete and its `OPTIONS` advertisement as the production store answered them when probed); they create no live identities or pods.
