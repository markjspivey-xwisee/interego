# I2IDL-X

An Interego / Foxxi **agentic superset** of the [I2IDL Digital Learning Glossary](https://www.i2idl.org/glossary) (release v0.0.80, 397 concepts), and a **semantic layer** for the digital-learning industry built on it. I2IDL-X decorates the glossary without copying or changing it. It makes the glossary actionable for agents (HyprCat hypermedia controls, Foxxi capability crosswalks, Interego context semantics, governed write paths), and it makes every I2IDL concept usable as a *type*: data that links to an I2IDL concept is typed in BFO 2020 (with IAO and CCO), gist, DOLCE-UltraLite, gUFO, PROV-O, schema.org and the peer learning vocabularies, by reasoners or by one SPARQL query.

Version 0.3.0. Built against `blakeplock/i2idl-linked-data@d73e73b` and verified against the live services — see `dist/verification-report.md` (0 failures). Independent work by Mark Spivey (Foxxi Mediums Inc.), drafted with Claude. Not affiliated with or endorsed by I2IDL.

> **Status: part of the Foxxi vertical — non-normative, not part of the Interego protocol.** In the Interego repository this package lives at `applications/foxxi-content-intelligence/i2idlx/`. It composes Interego primitives (signed context graphs on a pod, affordances, shapes checked on publish, ratification by modal status) and adds no term to `iep:`, `ieh:` or any other Interego namespace; its own terms are in the `i2x:` namespace, which is published on Interego itself. Build outputs are not tracked: `dist/` (the graphs, as published) and `site/` (the workbench and reference page) are regenerated by the build, the graphs are canonical at their Interego IRIs, and other publishers' vocabulary files are fetched by the refresh tools rather than redistributed.

## What's whose

Everything shown alongside I2IDL carries one of seven origin labels. They are data (`i2x:Origins` in the ontology, worded once in `src/origins.json`); the workbench and the reference page both render from them, and the build checks that every published graph is held by an origin.

| Origin | What it covers | Trust |
|---|---|---|
| **I2IDL** | Labels, definitions, editorial notes and status, types, fields, curated collections, broader / narrower / related, evidence and its classification, sources and their rights, the release. Served by id.i2idl.org. | Approved by I2IDL's editors. Canonical; never restated or edited here. |
| **I2IDL-X · derived** | Computed from I2IDL's own data with no claim about meaning: definition provenance, agentic kind, reuse class, release feed, change history, per-concept controls. | Deterministic; recomputed per release. |
| **I2IDL-X · added** | Links asserted about I2IDL concepts: a standard's specification document, a live exemplar. | Asserted by I2IDL-X, not by I2IDL. |
| **I2IDL-X · proposed** | Enactments, crosswalks, role capabilities, and the semantic layer (what each concept classifies, and its alignments). | Hypothetical until reviewers ratify. |
| **Interego** | Where I2IDL-X lives and how agents act on it: signed graphs, the catalog, ratification algebra, `publish_context` / `act`. | Signed; content-hashed. |
| **Foxxi** | The live learning capabilities enactments point to, concept-tagged xAPI, course alignment and coverage. | Foxxi's own services and contracts. |
| **Your team** | Votes, notes, usage marks; private packs and stars. | Visible to everyone the workbench admits. |

## The semantic layer

**Concept vs referent.** An I2IDL concept is a *term*: an information content entity about the things it classifies. `i2x:isClassifiedBy` links a thing in the world to the concept it is an instance of — this LRS deployment is classified by `i2idl:learning-record-store-lrs`, this quiz session by `i2idl:formative-assessment`. It is strictly instance-of; aboutness stays `dct:subject` / `schema:about`. The term itself is typed too (IAO and CCO information content entity, gist KnowledgeConcept, DUL Concept; per category also DUL EventType, Task, Role or Parameter and gist Behavior or Discipline), so the two levels never blur.

**Referent categories** (`i2idlx-referents`, Hypothetical). Every concept has exactly one of 35 categories (process, activity, learning activity, assessment, plan, method, programme, information artifact, specification, data format, data, credential, learning resource, model, norm, agent, person, organization, educational organization, group, disposition, competence, attitude, quality, measure, situation, software, application, web API, ecosystem, technology, material resource, discipline, no single category). 119 follow I2IDL's own type collection; 278 are decided by the definition where it says otherwise, each with a one-sentence `i2x:categoryRationale` and an `i2x:assignmentBasis`. Disciplines are subjects (link with `dct:subject`), and three concepts that name things of many kinds (xAPI Activity, emergent impact, source of influence) are deliberately left untyped. The graph also classifies I2IDL's own services with I2IDL's own concepts: the scheme is a controlled vocabulary, the SPARQL service an endpoint, Foxxi's profile an xAPI Profile.

**Alignments** (`i2idlx-alignments`, Hypothetical). Each category is an OWL class (`i2x:ProcessReferent`, `i2x:PersonReferent`, …) aligned once, with a rationale, to **BFO 2020 + IAO + CCO, gist 14.1, DOLCE-UltraLite, gUFO, PROV-O, schema.org, W3C ORG and DCMI**, and offered for publishing as the peer classes that describe such things (**CTDL, CTDL-ASN, ESCO, ELM, LRMI, ASN, Open Badges 3, CASE, xAPI, IEEE LER, ADL TLA**: a CTDL WorkRole for a role, a CTDL-ASN Competency for a competence) — export targets, not typings. The same graph types I2IDL's own record kinds (concepts, definitions, evidence, sources, collections, releases, changes), the Interego vocabularies (`iep:`, `ie:`, `ieh:`, HyprCat, HyprAgent) and Foxxi's LER and TLA classes. 215 aligned terms in 27 vocabularies; every one is checked to exist in a pinned snapshot of its publisher's file (`evidence/upper/`, 21 files with SHA-256). Upper ontologies are referenced, not copied.

**Crosswalks made executable.** A mapping proposal whose target is a *class* becomes an OWL bridge through `i2x:isClassifiedBy`: exactMatch ≡, broadMatch ⊒, narrowMatch ⊑ (32 bridges; the 15 close and related matches stay SKOS). So `xapi:Statement ≡ ∃isClassifiedBy.{i2idl:xapi-statement}`, and data typed only as an xAPI statement or an ADL TLA transactional LRS is classified without anyone writing `isClassifiedBy`.

**Inference: ABox into the TBoxes, three ways, one answer.**
1. **q-classify** — plain SPARQL 1.1 in the catalog, run client-side over the three semantic-layer ports plus your own data (`i2x:runsOver`). No reasoner. The build proves it sound and complete against OWL 2 RL for referent classes.
2. **SHACL-AF referent rules** — 58 TripleRules in `i2idlx-rules`, for SHACL engines without OWL (Interego's substrate executes this subset). They reach the same referent classes as OWL 2 RL on every explicitly classified resource.
3. **OWL** — an OWL 2 RL closure over the upper ontologies, I2IDL-X, I2IDL's whole release and a sample organization (36,517 → 145,866 triples, consistent), and HermiT (OWL 2 DL) per upper-ontology group: all consistent.

**Contradictions are caught.** 374 of the 595 pairs of referent categories can never share a member (disjoint in DUL 284, BFO 280, gUFO 181, PROV-O 80, gist 69, CCO 27 pairs); the build confirms each pair against OWL 2 RL. A thing classified as both a formative assessment and a classroom teacher is rejected under BFO, DUL and gUFO by OWL 2 RL and HermiT alike.

**A context graph for the industry.** `examples/industry-context.ttl` is a fictional academy's knowledge graph — its LRS, statements API, a teacher, a quiz session, a mentoring session, a MOOC run, a micro-credential, a skill, a policy, a team, a campus — classified with I2IDL concepts and nothing else. q-classify types its 17 resources 191 ways across all the upper ontologies. The catalog's `port-publish-classified` publishes such a graph to the organization's own pod; the relay validates it against the shapes first (the classifier must be an I2IDL concept, one category per concept). Any agent can then find it, type it and reason over it.

## Agentic, through hypermedia

**HyprCat catalog.** The glossary is a `hyprcat:FederatedDataProduct` in the ServiceWorld. Every port is simultaneously a `dcat:Distribution`, `hydra:Operation`, `iep:Affordance` and `ieh:Affordance`, so any of those dialects can act on it. 23 controls:
- **Output ports** on I2IDL's real service: JSON-LD and Turtle dumps, scheme, SPARQL with its published limits as data (`i2x:ServiceLimits`: 12,000-character queries, 30 requests per minute, 5,000-row caps, no Update/SERVICE/FROM) and as ODRL constraints, the human glossary. SPARQL has two ports: GET (`?query=`) for plain HTTP clients, and POST (`application/sparql-query`) for agents acting through Interego, which call `act` with the catalog, `i2x:act-query-glossary-post` and the query as a plain string payload.
- **Output ports on Interego**: the release feed, the change history, and the three semantic-layer graphs (`port-vocabulary`, `port-alignments`, `port-referents`).
- **Templated controls** (RFC 6570 over `dct:identifier`, `gs:activeDefinition`, `dct:source`) for per-concept resolution, expanded by the agent or materialized by the decorator projection.
- **Input ports** that write governed records to the caller's own pod through the relay — `propose-mapping`, `ratify`, `align-course-concept`, `publish-classified` — each with an input shape the HyperMarkdown projection renders as a form and `conforms_to_shapes` defaulted, so the relay rejects malformed records before writing. Foxxi ports (`record-usage` fronting `write-xapi-statements-signed`, `coverage`) and a human-mediated upstream-review control complete it.
- **11 stored queries**: nine run against the SPARQL ports (neighborhood, label search, definition + evidence, collection members, field intersection, by type, multi-field concepts, provenance profile, release check); two run client-side over the semantic-layer ports (`q-classify`, `q-concept-referents`). `$`-parameters are legal SPARQL variables, so each query runs as-is and binds by substitution.

**Decorators as data.** Five `ieh:AffordanceDecorator` individuals in an `ieh:DecoratorRegistry` declare the decoration program; `src/queries/build/decorations.rq` is its executable form and materializes five strictly followable controls per concept (Turtle, JSON-LD, definition, neighborhood, card). Each is self-identifying (its action is its own IRI, as in Interego's manifests), so `invoke_affordance(descriptor, action)` is never ambiguous.

## Design

**Decorate, never restate.** Every I2IDL concept keeps its IRI, label, definition, evidence and editorial relationships. I2IDL-X adds axioms, kinds, categories and controls *about* those IRIs. The ontology `owl:imports` the glossary and is a `prof:Profile` of the I2IDL scheme, so it is a superset in the literal sense. Concept-level controls are derived from the canonical graph rather than copied, which keeps I2IDL the single source of truth — the same principle its own roadmap sets for an agent API layer.

**Interpretant layers (Peirce, via Interego `ie:`).** The I2IDL definition is the *editorial* interpretant (`gs:Definition ⊑ i2x:EditorialInterpretant ⊑ ie:Interpretant`). I2IDL-X makes two more explicit: the *pragmatic* interpretant — the affordances that enact a concept, after the pragmatic maxim — and the *usage* interpretant, accrued from xAPI statements that tag the concept. Meaning stays editorial at the core and accrues from use at the edge.

**Agentic kinds.** Rules map I2IDL's 16 type collections to 8 kinds that say what an agent can do with a concept: Notion 182, Enactable 114, System 39, Standard 28, Domain 18, Framework 7, Actor 7, Normative 2. The mapping lives once, as `i2x:kindForTypeCollection` annotations; the rules are generated from them.

**Enactments.** 89 links from 78 concepts to 63 live actions (`operationalizedBy`, `realizedBy`, `implementedBy`, `measuredBy`, `recordedBy`, `credentialedBy`, `enforcedBy`, `explainedBy`): A/B testing → Foxxi `le-design-ab-experiment`, spaced repetition → `schedule-spaced-repetition`, human accountability in AI → `countersign-assessment`, LRS → `discover-lrs`, named graph → relay `publish_context`, and so on. Objects are action IRIs that 302 to the manifest defining target, method and input shape, so capabilities are linked, never redefined. 26 role capabilities turn I2IDL roles into agent role templates; the 18 for *learning engineer* are derived from Foxxi's own `[learning-engineer]` manifest tags. Inheritance along `skos:broaderTransitive` is an OWL property chain (7 inherited links).

**Mapping governance.** 62 SKOS crosswalk proposals are *records*, not triples: 25 from standards text, 13 cited by I2IDL's own evidence (UNESCO Thesaurus preferred terms, checked against UNESCO's Skosmos API), 24 AI-drafted. Targets: xAPI ontology 23, UNESCO Thesaurus 13, IEEE LER 8, ADL TLA 6, schema.org 5, xAPI Profiles 4, W3C VC 2, Interego 1. Every target was checked to exist in its vocabulary. A `skos:*Match` triple is materialized only when a proposal is ratified, by Interego's ratification algebra (Asserted = for, Counterfactual = against, Hypothetical = abstain). Shapes reject internal targets (I2IDL relationships stay I2IDL's editorial domain), non-mapping predicates, and any ratified lexical-only candidate — I2IDL's policy, enforced.

**Change history.** `i2idlx-changes` turns the public git history into PROV: 16 release changes since v0.0.54 (each `prov:used` the previous release and `prov:generated` the next), 52 typed change events (concept added, definition revised, relationship added, evidence classified or reclassified, source revised, …) covering 1,237 fact-level changes. It reconciles exactly with the current release, and every event type I2IDL's README names has a change kind.

**Foxxi integration.** Usage tagging reuses Foxxi's existing `foxxi#conceptIds` xAPI extension with I2IDL IRIs as values — no new extension. `i2x:CourseConceptAlignment` aligns Foxxi course concept-graph nodes to I2IDL so concept-coverage analysis can be read against one shared reference space across courses and tenants.

**Also included.** Upstream-contract shapes that check each new I2IDL release still has the shape the decorations assume (v0.0.80: 0 violations); definition-provenance classes (390 source-grounded, 7 synthesized), matching the provenance visibility I2IDL plans; a release feed (17 versions, v0.0.54 → v0.0.80); Interego interrogative alignments (What → definition, Why → editorial explanation, WhatKind → type, Where → field, Whose → evidence, How → enactment); and a JSON-LD context for Foxxi apps.

## How an agent uses it

`dist/agent-walkthrough.md` is a live, read-only run: read the published catalog and its limits → find "record store" with a stored query sent through the POST port exactly as Interego's follower sends it → follow the decorated neighborhood control (11 triples) → follow `realizedBy` to Foxxi `discover-lrs` (302 to the manifest) → `GET /xapi/about` (200) → follow the three semantic-layer ports `q-classify` names and type the sample organization locally (191 typings of 17 resources) → stop at the two writes (record usage, propose mapping) and show their payloads.

The same paths run through the Interego connector itself: `invoke_affordance` on `act-get-scheme` and on `act-get-referents` (the referents graph, 1,210 triples, identical to the build), and `act` on `act-query-glossary-post`, all return live data. Pass the catalog IRI itself as `descriptor_url`; it stays stable when the catalog is republished, unlike the signed descriptor's URL. For a capability found in the enactments, pass the manifest its action IRI redirects to (for Foxxi, `https://foxxi-bridge.interego.xwisee.com/affordances`). `dist/preview/*.hmd.md` shows the HyperMarkdown the relay serves, rendered with Interego's own renderer.

## Verification

`build.py` refuses to emit any crosswalk row whose concept is not in the pinned release, whose action is not in the live Foxxi manifest or relay operations catalog, or whose external target does not exist. It then checks parsing, the origin labels, the upstream contract, SHACL-AF rules, superset shapes (and negative tests that the shapes reject what they claim to), the change history's reconciliation, the semantic layer (every aligned term in its snapshot, one category per concept, OWL 2 RL closure and consistency, HermiT per upper-ontology group, I2IDL's records typed as intended, the sample organization typed as expected, crosswalk bridges, SHACL rules vs OWL 2 RL, the category clash, the disjointness table pair by pair), stored queries (q-classify sound and complete), the decorator projection, Interego's own `extractAffordancesFromTurtle` and HyperMarkdown renderer, and worked examples. With `--live`: all linked action IRIs dereference, materialized targets resolve, the live SPARQL endpoint returns the same provenance profile as the local run, every read-only catalog port answers when sent the way Interego's follower sends it (the port's `dcat:mediaType` as Content-Type and Accept, no body on GET, a string payload as-is), and each graph's `/ns` IRI is reported as published-and-identical, published-but-different (republish it) or not yet published.

## Things to know

- Everything proposed — enactments, crosswalks, referent categories, alignments — is published Hypothetical on purpose; a reasoner using it reaches Hypothetical conclusions, and it needs review before ratification.
- I2IDL collection IRIs (`/collections/...`) return 404 upstream; only scheme, concept, definition and source IRIs dereference. The catalog reaches collections through SPARQL for that reason.
- Foxxi's LRS reports an in-memory backend ("lost on restart") in its live `/xapi/about`, so usage interpretants are only as durable as wherever the statements are persisted.
- Templated controls are for agents to expand; Interego's strict follower only invokes controls with a concrete `hydra:target` (17 in the catalog, 1,985 in the decorations), and the relay's HyperMarkdown marks the other six DECLARATIVE.
- Interego's follower sends no payload on a GET, so a GET control whose input belongs in the URL (the SPARQL GET port) is for plain HTTP clients; agents use the POST port. The build's follower check catches regressions of this kind.
- `publish_context` takes each graph inline, so publish the file verbatim. The publish path strips four leading spaces from lines inside multi-line literals, so stored queries are indented at most three spaces; the build refuses deeper indentation. The build's published-state lines and `tools/verify_published.py` flag any drift between what is live and the build.
- The relay validates a publish only against shapes that target something in it: the catalog and referents are checked on publish; the alignments graph has nothing the shapes target, so the build checks it locally.
- Large upper ontologies are snapshotted as upward modules around the terms used (each term, its named superclasses and superproperties, domains and ranges, and the disjointness axioms among them). Credential Engine refuses scripted downloads, so CTDL and CTDL-ASN terms are recorded from the published class index.
- `dcat:mediaType` is a literal, as Interego's extractor reads it, rather than a DCAT 3 media-type IRI.
- Default license CC BY 4.0, matching I2IDL-original content; change it in `src/i2idlx.ttl` if you prefer Interego's MIT.

## Interpretant — the workbench

`site/app.html` is **Interpretant**, a working app over the glossary and these graphs, hosted as a Claude artifact (private until its owner shares it; `appArtifactUrl` in `config.json`). It is built from the same pinned sources by `tools/build_app.py`, which re-checks what it derives: kinds and definition provenance against the rules' output, all 1,985 decorated control targets against the client's own recipe, every enactment action against the live manifests, and the semantic layer against the published graphs and the build's reasoning record.

Every zone carries its origin label, and an **I2IDL only / + I2IDL-X** lens hides every layer to show the glossary exactly as I2IDL publishes it.

- **Lexicon** — instant, typo-tolerant search and facets; entries read like a dictionary: I2IDL's definition and editorial note as hypertext, relations, evidence with each source's rights, the eight Interego interrogatives, per-term history, and the layers: what enacts it, crosswalks with the target's own definition, what it classifies in every ontology, team notes, and the controls an agent follows.
- **Map**, **Compare**, **Annotate** (paste any text and see every I2IDL term in it, linked to its entry and IRI, then turn the set into a pack, xAPI concept tags or linked Markdown), **Packs** (course glossaries with exports, including Foxxi `conceptIds` xAPI tags and `i2x:CourseConceptAlignment` Turtle).
- **Review** — the shared queue for the 151 Hypothetical enactments and crosswalks. Votes compose under Interego's ratification algebra; a quorum policy decides each item; exports are `port-ratify` calls and a team ledger, and ratified crosswalks open the catalog's upstream-review control.
- **Semantics** — the alignment matrix (35 categories × every ontology) with each category's concepts, reasons and clashes; a **Playground** that classifies pasted Turtle in the browser and flags contradictions, with the same results as q-classify; how I2IDL's records and the platforms are typed; the reasoning record; and the agent recipe.
- **For I2IDL** — what this layer adds to I2IDL's glossary, mapped to I2IDL's own roadmap, with an editorial packet to export.
- **Insights**, an **Agent console** (published graphs, every port with its input shape, the stored queries runnable on the embedded release and live, the capability directory, an agent brief), and **Ask Claude**, which reads the release through page tools and cites terms as `[[concept-id]]`.

Shared state lives in the artifact's database under declared rules: `ballots/`, `notes/`, `usage/` are readable by everyone the page admits and each person writes only their own document (Contributor access or above); `settings/policy` is editors-only; packs and stars are private to each viewer. Signed-out visitors get the full read-only app. Ask Claude runs on each viewer's own Claude account.

## Rebuild

Machine-specific paths live in `config.json` and can be overridden with environment variables; a relative path is read from this directory. `I2IDL_CLONE` is a clone of `blakeplock/i2idl-linked-data` (checked out at the pinned release). `INTEREGO_CORE_SRC` and `INTEREGO_TSX` point at Interego's `packages/core/src` and a `tsx` binary, so the build can run Interego's own affordance extractor and HyperMarkdown renderer; inside the Interego repository they default to the repository's own.

```bash
pip install --break-system-packages rdflib pyshacl owlrl owlready2   # owlready2 bundles HermiT; it needs a Java runtime
bash tools/refresh-evidence.sh         # network: Foxxi affordances, relay operations, xAPI, LER, TLA and iep vocabularies
python3 -I tools/refresh_upper.py .     # network: upper-ontology and peer-vocabulary snapshots → evidence/upper/
python3 -I tools/refresh_unesco.py .    # network: UNESCO Thesaurus terms I2IDL's evidence cites
python3 -I build.py --live              # needs the local I2IDL clone and the fetched evidence; see config.json

# Reproduce the published graphs byte-for-byte (the stamps they carry):
I2IDLX_BUILT_DATE=2026-10-08 I2IDLX_MODIFIED=2026-10-09 I2IDLX_NOW=2026-10-09T18:14:15+00:00 \
I2IDLX_NOW_ENACTMENTS=2026-10-09T03:35:48+00:00 I2IDLX_NOW_RELEASES=2026-10-09T03:35:48+00:00 \
python3 -I build.py --live

python3 -I tools/verify_published.py .      # every /ns IRI serves exactly dist/ (Turtle and JSON-LD isomorphic; Markdown resolves)
python3 -I tools/publication_record.py .    # refresh dist/published.json from publications.json
python3 -I tools/agent_walk.py . > dist/agent-walkthrough.md   # the live, read-only agent walk
python3 -I tools/build_site.py .            # → site/index.html
```

Without the pins, a rebuild stamps the current date and time into the graphs that carry one, and the build's published-state lines will then ask for those graphs to be republished. A full build takes about six minutes, most of it reasoning.

`evidence/` holds the snapshots everything was checked against: the Foxxi manifest summary, relay operations, the xAPI, xAPI Profiles, IEEE LER and ADL TLA vocabularies, the UNESCO terms, the peer-vocabulary term index, and `upper/manifest.json`, which records the pinned source, version, license and SHA-256 of each upper-ontology and peer-vocabulary file (BFO, IAO, CCO, gist, DUL, gUFO, PROV-O, schema.org, ORG, DCMI, DCAT, LRMI, ESCO, ELM, ASN). Those files, like the xAPI and xAPI Profiles ontologies, are other publishers' work: the package references them rather than redistributing them. `tools/refresh_upper.py` and `tools/refresh-evidence.sh` fetch them again before a rebuild, together with snapshots of Interego's namespace files (`evidence/interego-*.ttl`, the same files as `docs/ns/` in the Interego repository).
