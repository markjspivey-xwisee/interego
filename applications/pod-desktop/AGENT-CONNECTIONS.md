# Connect an agent to your local pod

**Layer 3 Windows application, preview.** These connections use the installed Interego app. They do not change the hosted service or enable federation.

1. Open Interego and set up or restore your local pod.
2. Open **Connections**, choose **Connect an app**, and select the client that runs on this computer.
3. Name the connection, choose its permissions and expiry, then create it. Read access is selected by default; saving notes is a separate choice.
4. Follow the app's setup instructions. Copy the configuration into the selected client's settings, preserving its other entries. If you use a copied command, run it in **PowerShell**.
5. Reconnect the client and ask it to check its Interego connection. **Waiting for first use** becomes **Last used** after authenticated activity; creating or copying setup alone does not prove a connection.

Keep Interego open. **Stop Interego** pauses note access; quitting stops both the pod and the local connection service. **Disconnect** remains available while the pod is stopped. An expired or disconnected connection needs a new grant.

## Choose permissions

**Read notes** allows the connection to search and open any of this pod's current and future notes until the grant expires or is disconnected. Search returns titles and short excerpts; reading a note retrieves its full text.

**Save new notes** allows appending new notes. It does not allow editing or deleting existing notes and does not imply read permission. Notes saved through a connection retain its identifier and chosen label in encrypted content. That label is not proof of a vendor's identity or a vendor signature.

**Notes an agent reads may be sent to its AI provider.** The pod stores private content locally, but that does not make the agent's model inference local. Disconnecting stops future Interego access; it cannot retract information a service has already received. These grants control the Interego tool surface, while an agent host manages its other permissions on your computer.

The app keeps its pod encryption key and storage credential. Each connection has a separate Windows-protected credential, and setup text contains only a command, connection identifier and local profile path. Notes backups preserve notes and historical authorship, not connection credentials. Restoring notes on another installation does not silently reconnect agents.

## Client setup

The app generates the actual installed paths and connection identifier. Use those values rather than pointing a second copy of the generic Interego server at the app's storage.

| Client on this computer | Setup generated by Interego |
|---|---|
| ChatGPT desktop | Local STDIO settings or the shared Codex TOML configuration |
| Codex CLI / IDE | Codex TOML plus an optional PowerShell registration command |
| Claude Code | Local stdio JSON plus a PowerShell registration command |
| Claude Desktop | Local `mcpServers` JSON configuration |
| Grok Build | Local MCP TOML configuration |
| OpenClaw | `mcp.servers` configuration for a Gateway on this computer |
| Another MCP client | A standard local stdio command, arguments and environment |

ChatGPT desktop and Codex share MCP configuration; available settings can be restricted by the account or organization. See [OpenAI's MCP documentation](https://learn.chatgpt.com/docs/extend/mcp?surface=cli). Claude Code uses its [local stdio connection route](https://code.claude.com/docs/en/mcp); Claude Desktop uses [local MCP server setup](https://support.claude.com/en/articles/10949351-getting-started-with-local-mcp-servers-on-claude-desktop). Grok Build and OpenClaw describe their formats in [Grok Build MCP servers](https://docs.x.ai/build/features/mcp-servers) and [OpenClaw MCP connections](https://docs.openclaw.ai/tools/mcp).

The formats were checked against current official documentation. Codex and Claude Code CLI syntax was also checked locally. The packaged executable is exercised with a real MCP protocol client, but this is not a claim that every vendor client or account was signed in and tested.

## Web and cloud agents

A web connector or a process on another computer cannot start this Windows command or use its loopback address. In particular, [Grok Bot's cloud computer](https://docs.x.ai/grok-bot/computer-and-apps) is distinct from Grok Build running on your PC. Claude's [remote connectors](https://support.claude.com/en/articles/11175166-get-started-with-custom-connectors-using-remote-mcp) also run through hosted infrastructure.

An optional remote-access transport would need a separately configured, authenticated bridge. This preview does not open a tunnel or publish your local pod. **Use hosted Interego** continues to open the existing hosted service; it does not copy local notes or grant hosted access to this pod. Cloud-only connection setup is a separate milestone.

## Implementation and verification

The bundled executable's `--mcp-stdio` mode is a transport companion. It never starts another pod or loads the pod's content key. It reads only its connection ticket, speaks MCP over stdin/stdout, and contacts the app's loopback broker. The broker encrypts and authenticates messages with per-connection keys, fresh session binding, request identifiers and replay protection; credentials and note text are not sent as plaintext over that local hop.

The app checks grants again when queued note operations execute, binds them to the current pod, and rejects revoked, expired, disconnected or mismatched connections. Tool discovery is permission-filtered, and operation handlers enforce the same permissions. There are no agent tools for backups, restore, grant management, arbitrary URLs, shell execution or federation. At the connection limit, old inactive grants can be pruned while current grants remain intact.

The packaged verification launches separate copies of the actual executable in stdio mode. It tests read-only and save-only grants, private-note creation and retrieval, bounded search excerpts, revocation of an open MCP session, and persistence after a runtime restart. Backend tests additionally cover corrupted credentials, request/response binding, replay, expiry, pod changes, browser origins, request limits, cancellation and queued authorization. The existing hosted and stdio configuration tests remain regression checks.
