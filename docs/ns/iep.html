Interego Protocol vocabulary iep:

Namespace https://markjspivey-xwisee.github.io/interego/ns/iep# · version 1.0 · 524 terms.

This is the namespace document for https://markjspivey-xwisee.github.io/interego/ns/iep# — the Interego Protocol (L1) vocabulary: the classes and properties an agent uses to publish, compose, and reason over context on the substrate. Terms are identified by hash IRIs under this base (e.g. iep:modalStatus = …/ns/iep#modalStatus).

Machine-readable form: iep.ttl (Turtle) — the authoritative source. This page is a human-readable projection of it.

Terms

Every term iep.ttl declares, projected here so an IRI a reader follows resolves to a page that actually mentions it. This page carried four of them until 2026-08-21; the other 505 dereferenced to a document that did not name them.

iep:AccessControlPolicy Class
An attribute-based access-control policy, expressed as a first-class context descriptor. A policy carries: (a) iep:policyPredicate — a SHACL shape the subject's attribute graph must satisfy; (b) iep:governedAction — the action (affordance / operation) the policy governs; (c) iep:deonticMode — one of iep:Permit, iep:Deny, iep:Duty; (d) optional iep:policyDuty — obligations to fulfil when Duty mode matches. Attribute sources for the subject can span the federation — the evaluation pattern for that resolution is specified by the abac: L2 ontology, but the structural primitives live here at L1 so that any implementation understands the same policy shape.
iep:actedOnOwnAccount Object property
PER-ACT, and the explicit negative of a prov:Delegation over the same activity: in this one activity the agent acted on its own account, so no other agent retains responsibility for its outcome and the agent alone is accountable for it. The subject is the agent — the same position prov:actedOnBehalfOf takes — and the object is the single activity the statement is scoped to. It exists because PROV-O has no negative form: prov:Delegation is defined as assigning authority 'to carry out a specific activity as a delegate or representative, while the agent it acts on behalf of retains some responsibility for the outcome of the delegated work', and the ABSENCE of one states nothing at all. A reader that took absence for own-account would be defaulting; a reader that took it for on-behalf-of would launder an agent's own words into its delegator's. Absence is therefore a third answer — not stated — and neither of the two. An activity MUST NOT be both the prov:hadActivity of a prov:Delegation and the object of this property; a reader that finds both reports the disagreement rather than choosing. Standing delegate status is untouched by this: that is a fact about the AGENT, published and revocable on its delegator's pod, and it stays true whichever footing any act was on.

iep:addressedTo Object property
The agent or agents a record is a request TO, stated inside the record's own signed region. ★ IT IS HERE AND NOT IN A VERTICAL'S VOCABULARY BECAUSE ADDRESSING AN AGENT IS NOT SOMETHING A ROOM INVENTED: a workspace entry, a Foxxi record and a bare script's record must all spell it identically, or an agent that reads two of them gets two answers to one question — and an agent that belongs to no room could not be addressed at all. ★ AND IT IS IN THE SIGNED REGION RATHER THAN IN THE NOTIFICATION THAT ANNOUNCES IT BECAUSE AN INBOX IS WORLD-WRITABLE. A notification is a POINTER and never the request: it carries no task text, because text that travelled by inbox is text a forger could write. What makes the pointer safe to follow is that the record it names is signed and content-bound, and that its recipient checks the party that delivered the pointer IS the party that signed the record. A reader MUST NOT treat its own absence as anything: a record addressed to nobody is a record, not a request.

iep:askVia Object property
HOW TO REACH AN AGENT THAT HAS NO ENDPOINT — the explicit alternative to hydra:target, and the reason a capability document is not obliged to carry one. An agent running on somebody's laptop, on their own model credential, behind whatever network they are on, has nothing that will ever answer a POST; publishing a hydra:target for it would advertise a call that cannot connect. This names the route instead: put a signed record where the agent reads, and it answers when its host next runs. A capability document MUST declare exactly one of hydra:target and iep:askVia. Neither means an agent reachable by no route at all, which is worse than advertising nothing; BOTH leaves a reader choosing which of two ways is the real one with no honest basis, and a reader that finds both MUST refuse rather than choose.

iep:canonicalId Object property
The location-INDEPENDENT canonical URL form of a projected node's identity, derived deterministically from its iep:pgslUri (urn:pgsl:<kind>:<hash> -> https://relay.interego.xwisee.com/ns/pgsl/<kind>/<hash>). Same content yields the same canonicalId on every pod, so it preserves the federation-overlap property of the urn while being a dereferenceable URL that actually RESOLVES at its authority (the relay redirects it to a public-lattice resolver, w3id.org-style) — the identifier both denotes (this id) and resolves to connotation (the node's description). Additive to iep:pgslUri, which remains the internal content-address key (never re-identified).

iep:ControlSet Class
A named, PUBLISHED set of controls that a conformance report scores against. ★★ IT EXISTS BECAUSE THE SCOPE WAS A FROZEN ARRAY IN CODE. When true the relay is not among the envelope's recipients and cannot read the payload: it received ciphertext, stored it verbatim, and iep:renderView is therefore NOT advertised because no server-side projection is possible. When absent or false the payload was sealed by the relay, whose own key is a recipient — so the operator can read it. This is a statement about who can read a record, not about how it was transported, and it is per-record on purpose: a workspace that changes over to publisher-sealing contains records on both sides of that line permanently, because an envelope's recipient set is fixed when it is written and re-sealing would require the very key being removed.

iep:shapeDeclaresNoShapes Constraint component
A caller-declared shape WAS fetched and DID parse, but the document declares no SHACL shapes at all, so validating against it would have conformed without checking anything. Distinguished from iep:shapeUnfetchable because nothing failed: the retrieval succeeded and the verdict was a correct trivial pass (SHACL conformance is vacuous over an empty shapes graph). The publish is refused because a conforming report over zero shapes is byte-identical to a genuine clean pass, so reporting it as success would confirm something adjacent to what was asked. Usually raised by naming an ontology IRI, a profile IRI, or a descriptor URL where a shapes graph belongs — a descriptor holds facets rather than shapes, and an ontology commonly keeps its shapes in a separate document. Raised ONLY for shapes the caller named: a container's own iep:conformsTo / dct:conformsTo is a profile assertion the caller does not control, and refusing it would lock the pod out of the write that would correct it, so that case is reported in the publish response instead.
iep:shapeUnfetchable Constraint component
The publish gate SENT a request for a declared shape and did not get a usable shapes graph back — a 404, a 5xx, a timeout, or a page whose advertised Turtle representation is gone. Conformance to a shape that cannot be read cannot be asserted, so the publish is refused rather than proceeding unvalidated. Says nothing about WHY the host answered as it did; the shape may have been withdrawn or its host may be down.
iep:shapeUnfetchableEgressRefused Constraint component
NO REQUEST WAS SENT. The relay's egress screen refused the declared shape's target because its host is, or resolves into, private or internal address space — a caller-supplied shape IRI is an SSRF vector, so the screen runs before any socket is opened. Distinguished from iep:shapeUnfetchable because nothing whatever is known or implied about the named host, the refusal is deterministic rather than transient, and the remedy is to declare a shape on a publicly reachable host rather than to retry. The resolved address is deliberately NOT carried in the message: it is internal topology for any host whose name does not already encode it.
iep:shapeUnfetchableScheme Constraint component
A declared shape IRI can NEVER be fetched because its scheme is not https. Distinguished from iep:shapeUnfetchable because it is a configuration error in the caller's own declaration rather than an outage: no host was consulted, and no retry will ever succeed.
