# Generic hypermedia client

A descriptor-driven client for Interego / HyperMarkdown / Hydra documents. You give it any authority URL. It discovers every control, builds a form from the advertised fields, resolves the live `hydra:target` at invocation time, and renders the response. Nothing in the client is specific to the I2IDL glossary — that catalog is only the first document it was tested against.

These files live in `docs/hypermedia-client/`. GitHub Pages publishes the `docs/` folder on `master`, and `docs/.nojekyll` is already present, so Jekyll does not rewrite this directory.

## How to run

CLI:

```bash
python3 hmc.py list https://relay.interego.xwisee.com/ns/u-pk-33d42e6b33dc/i2idlx-catalog
python3 hmc.py describe URL act-get-scheme
python3 hmc.py invoke URL act-get-scheme
python3 hmc.py invoke URL act-query-glossary   --field query='SELECT (COUNT(?c) AS ?n) WHERE { ?c a <http://www.w3.org/2004/02/skos/core#Concept> }'
python3 hmc.py invoke URL act-rest-listConcepts --field limit=2
python3 hmc.py invoke URL act-propose-mapping --field graph_iri=x --field graph_content='@prefix : <urn:x:> . :subject :predicate :object .'
```

The last command is a dry run: unsafe operations never send unless you pass `--confirm`. Its values have to satisfy the shape the catalog publishes: on 2026-11-15 that asked for a `graph_content` of at least 40 characters. Both clients check a shape's required fields, lengths, ranges and enumerations, that a number field holds a number of its type, and that a date or a time is written as XSD writes one, before they plan a request, and leave patterns to the server; a constraint neither checks refuses the value rather than send it (see [Values](#values)). A number field's enumeration is checked by value, so `1` matches an entry written `1.0`. An integer or decimal that a JSON number would change is refused rather than rounded, so an integer field's value stops at 2^53 - 1 in both clients; a double or float field takes the double nearest what was typed.

Web app: use the hosted page, open `index.html` directly as a file, or point any static server at this directory. There is no build step and nothing to install.

The web app reads JSON-LD and HyperMarkdown, not Turtle. When a host answers in Turtle, the page asks it again with `?format=jsonld`. For a host that serves only Turtle, use `hmc.py`, which reads Turtle when `rdflib` is installed.

Deep link example:

```
index.html?url=https://relay.interego.xwisee.com/ns/u-pk-33d42e6b33dc/i2idlx-catalog&invoke=act-query-glossary&query=SELECT%20(COUNT(%3Fc)%20AS%20%3Fn)%20WHERE%20%7B%20%3Fc%20a%20%3Chttp://www.w3.org/2004/02/skos/core%23Concept%3E%20%7D
```

### The proxy field

The proxy field is optional, and it is empty unless you type into it. The page never fills it from its own address, so a link cannot route your requests through someone else's server.

It takes the absolute `https://` URL of a CORS proxy you run yourself. The page sends each request to that URL with the target appended as a `url` query parameter (`<proxy>?url=<encoded target>`, or `&url=` when the proxy URL already has a query). Use it only for a descriptor host that does not send `Access-Control-Allow-Origin`.

The targets the page hands a proxy are the ones it would fetch without one: `https` URLs only. It also never hands a proxy a loopback, private, link-local or shared address written as a literal, or a `localhost` name, because a proxy on your own machine can reach those and the page cannot. A public name that resolves to such an address is not caught by the page; only the proxy sees the address a name resolves to, so a proxy you run should refuse those itself.

A proxy sees every request sent through it, including the body of any write you confirm. Use one you control.

The address the page sends to through a proxy is the proxy's, so a dry run shows it as `via`, next to the target's `url`. A proxy may also follow a redirect itself, which the page cannot see or stop: a write sent through one that does may be re-sent to another address. The page sends a write with `redirect: "manual"` either way (see [Writes go where they say](#writes-go-where-they-say)), so a redirect the proxy passes back is reported as not done, but only a proxy that does not follow redirects keeps a write at the address shown.

This directory used to ship a local forwarding proxy, `proxy.py`. It was removed: a server that fetches whatever URL it is handed has to defend every address it can reach, and the hosted page does not need one for the hosts it was written against.

## How target resolution works

HyperMarkdown projections print a `target` that is often the document's own action junction (`#control-…`). The markdown itself says that projection may be stale and that the signed descriptor is the authority.

The client therefore:

1. Fetches the authority document, preferring JSON-LD (`Accept: application/ld+json`, then `?format=jsonld`), then Turtle (read by `hmc.py` when `rdflib` is installed; the page cannot parse it), then HyperMarkdown `:::control` blocks. Both clients take the same steps:
   - An answer counts when its status is 2xx and its body, read as `fetch` reads one (UTF-8 with a byte order mark dropped, and two `Content-Type` headers joined by `, `), is JSON-LD, Turtle or HyperMarkdown. A 3xx with no `Location`, or an empty one, is not followed, as a browser does not follow it, so it is an answer that does not count. An answer is read to 8,388,608 bytes and no further, whatever its status, as a response is (see [Work](#work)); one longer is not read, and the request ends as one that gets no answer does, named (`The answer to https://… is larger than 8388608 bytes, so it was not read.`).
   - An answer that counts but is not JSON-LD is asked for again as `?format=jsonld`, unless the address names a format the client reads (`hmc.py` without `rdflib`, like the page, asks again for one that names Turtle). That retry is optional: when it gets no answer, or answers anything but 2xx JSON-LD, the first answer is read as if the retry had not been asked. JSON-LD it answers is the authority for the first answer, so when the client refuses it (see [Fail closed](#fail-closed)) the first answer is still listed, but not read as safe: the JSON-LD's problem is named with it, and every control in it is listed as unsafe and refused with that problem, since what the authority says of each is not known. When the first answer is not read either (Turtle, on the page), the load ends with the JSON-LD's problem named.
   - When the address names no format and its answer does not count, `?format=jsonld`, `turtle` and `markdown` are asked in turn.
   - A request that gets no answer at all (the connection fails or closes, a redirect leaves http(s) or goes past the 20 `fetch` follows, or it times out) ends the load with its problem named, unless it was the optional retry. `hmc.py` gives up on a request after 60 seconds without data; the page leaves that to the browser.
2. Indexes every node object in the document, wherever it is written, merging the descriptions of one `@id` into one node, and walks `iep:affordance` / `hmd:control` / `hydra:supportedOperation` / `hydra:operation`, plus any node typed `hydra:Operation`, `iep:Affordance`, or `hmd:Control`, or naming a `hydra:method` and an action, a target or a template, wherever the document puts it: at the top, in `@graph` (and a named graph's `@graph` within it), in `@included`, in an `@index` or `@id` map, or written in place inside another node.
3. Reads the live `hydra:target`, `hydra:method`, `hydra:expects`, `hydra:returns`, `dcat:mediaType` / `hydra:returnsContentType`, and any linked `hydra:IriTemplate`. Every IRI in a JSON-LD document, each `@id` and each value of a term its context types as `@id` or `@vocab`, is expanded first, through the document's prefixes and `@vocab`, and a relative one is resolved against the context's `@base` or else the address the document was fetched from. So `{"@id": "/api"}` is an address on the descriptor's host, and `{"@id": "xsd:integer"}` is XSD's integer. The context is read as JSON-LD 1.1 reads it: keyword aliases (`"id": "@id"`), properties nested under `@nest`, a term defined before the prefix it uses, a term with no `@id` under `@vocab`, a node's own `@context` and a term's or type's scoped one, container maps, and `@json` value objects. The base is the address the document landed at after redirects, so `/dir` answered from `/dir/` puts `items` at `/dir/items`; after a 303 See Other `hmc.py` keeps the address it asked for, as JSON-LD says, and the page, which cannot tell a 303 from another redirect, uses where it landed. Resolution follows RFC 3986 on the text as written, so an IRI keeps its non-ASCII characters and `"@vocab": "#"` keeps its `#`; a request carries the URI form, written as a URL parser writes it (see [Safety](#safety)). A document with more `@context` work than a fixed budget is refused rather than read slowly, and so is JSON nested deeper than 256 arrays and objects, in a document or a value (see [Values](#values)), and one whose prefixes, terms, `@vocab` and `@base` expand its IRIs to more text than eight times its own length and 1,000,000 characters besides, counted in UTF-16 code units as it is read: each IRI they expand to, keys included, and, once, what each plain string it holds would expand to as a node's name (`This document's prefixes, terms, @vocab and @base expand its IRIs to far more text than the document holds, ...`), so one long prefix that many short compact IRIs use cannot make reading it cost far more than its size. Those limits, and the ones below, name their own problems; past them, one budget of work for each step (see [Work](#work)) refuses by name any other shape of document that would make a step cost far more than its size. A node many nodes name, a template or shape many controls share and a class many nodes name are each read once, a property node a shape or a class names many times is one input, as RDF reads a value given twice as one, and a control's fields are built when it is opened or invoked. What `hmc.py` writes grows with the document too. `list` writes the fields several controls share once, with the first of them, and names that control for the others, and a template's variables, which follow a control's own fields, once for every control that shares the template (`fields: x1, and the template's variables as listed for urn:c0`). `list --json` writes each field once, in `fields`, however many shapes or controls share it, each `sh:in` list once, in `inLists`, which a field names by its place as `in`, and each list of fields once, in `fieldLists`, as the places of its fields; each control names its own list's place as `fieldList`, and the place of its template's variables, which follow its own, as `templateFields` (null where its fields are one list). A control whose own fields a mapping of its template matches, or whose schema types the template's variables (`additionalProperties`, or a closed shape), joins the template for itself, so `list` builds so many of those as the document's size allows, a field for every 64 characters and 128 besides, and lists the rest without their fields or the problems they would give (`fields: not listed, ...`; `unlisted` in `list --json`), which `describe` and `invoke` build, as the page builds a control's fields when it is opened. Neither `list` nor `describe` writes the fields of a control that is not invoked (`fieldList` and `fields` are null), as the page shows it no form.
4. Classifies transport:
   - **http** — `hydra:target` is a normal `http(s)` URL, or a `hydra:IriTemplate` (written as the `hydra:target` itself, as Interego's decoration catalogs do, or reached by `hydra:search`) expands to one. A relative template resolves against the base. A GET sends no body: its fields go in the query, and a field that is a whole request body goes there as a parameter named after it (this is how SPARQL `?query=` works). A body sent whole is labelled by its own type (JSON, a SPARQL query, or plain text); the control's media type is what it returns and goes in `Accept`.
   - **mcp** — `hydra:target` is an Interego tool junction (`https://<interego-relay-host>/tool/...`). A GET of `https://relay.interego.xwisee.com/tool/publish_context` returns HTTP 404 and CORS there is origin-restricted to the relay itself. These writes go through the Interego relay MCP: `invoke_affordance({descriptor_url, action_iri, payload})` or `act({descriptor_url, action_iri, method, payload})`. The client shows that call and does not POST it over raw HTTP.
   - **junction** — the target is a fragment of the descriptor itself, whether written `#control-…` or in full; once resolved, the two are the same IRI. The client tells you to use the authority document or MCP `invoke_affordance`.

The Interego `act` kernel verb was verified against `act-get-scheme`: given the catalog URL and that action IRI, it re-resolved `hydra:target` to `https://id.i2idl.org/scheme.ttl` and returned the same Turtle as a direct HTTP GET.

SHACL `NodeShape` property constraints (name, datatype, minCount/maxCount, pattern, defaultValue, maxLength/minLength, description, `sh:in` as a plain array, an RDF list or a JSON-LD `@list`, min/max inclusive and exclusive bounds, `sh:hasValue`, `sh:nodeKind`) become form fields, and so does each `hydra:supportedProperty` of a `hydra:Class` (named by its property's IRI, or by the label of a property written in place, as Interego's manifests write one). A SHACL property with no `sh:maxCount`, or one above 1, takes a list, as Interego's own shapes mean it (a single value carries `sh:maxCount 1`): on the page one value per line or a JSON array, or a multiple select when it has choices; in `hmc.py` the `--field` repeated. It is sent as a JSON array, or as an RFC 6570 list in a template, and its count is checked against `sh:minCount` and `sh:maxCount`. A field that takes one value takes the last one given. A name that is no field's is refused, not dropped, and a control with two fields of one name is not invoked. A `pattern` is shown next to its field and left to the server to enforce: neither client runs a regular expression from a remote document, because a crafted one can take time exponential in the input. If `hydra:expects` is an inline JSON Schema object (as on the Foxxi affordance manifest), those properties are used instead. Hydra template variables are merged onto the same fields.

JSON Schema `object` and `array` properties, SHACL properties with `sh:node` or `sh:nodeKind sh:BlankNode`, and `rdf:JSON` datatypes are parsed as JSON; a node shape whose own datatype is `rdf:JSON` takes a request body that must parse as JSON, and sends it as written. A field such as Foxxi's `document` or `concept_ids` is sent as a real object or array in a JSON body, and a list is expanded as an RFC 6570 list when it fills a URI template. Other fields stay strings.

URI templates use RFC 6570 percent-encoding of UTF-8 (`encodeURIComponent` semantics). `café` becomes `caf%C3%A9`. A `+` operator still leaves ASCII reserved characters unescaped.

## Fail closed

Both clients read the JSON-LD forms they model, and fail closed on the rest. Where a property that decides safety, method, target, datatype or cardinality has more than one distinct value, or a document uses a JSON-LD structure the reader does not model, the control is listed as unsafe and refused with a problem that names it, or the whole document is refused with a named problem. Neither client reads the first of several values, or skips a form it does not read; where the choice is between refusing and reading more of JSON-LD, they refuse.

- Every node object is indexed wherever it is written, and the descriptions of one `@id` are one node, as JSON-LD merges them: a hint, a method or a target written on an object with a control's `@id`, under any property or inside another `@graph` node, is the control's, and so is a template or a shape written in place with an `@id` the document describes elsewhere too. A node with no `@id` is a blank node, its own node: it never takes its action, or the label it is shown by, as an `@id`. Two nodes that name one action are refused, whatever each sends; one node named twice is one control.
- Everything that decides what a control does is read with all its values, merged descriptions of one `@id` included: `hydra:method`, `hydra:target`, `hydra:template`, `iep:action`, the hints, `hydra:expects`, the media type, a template mapping's variable, property and `hydra:required`, and an input's `sh:path`, `sh:name`, `sh:datatype`, counts, lengths, `sh:pattern`, `sh:in`, `sh:defaultValue`, bounds, `sh:hasValue`, `sh:nodeKind` and `hydra:writable`. More than one distinct value, or a value in a form not read there (a `@list`, a JSON literal, a node written in place with no `@id`, a malformed RDF list, a count that is not a whole number of zero or more), lists the control with the writes and refuses it with a problem that names the property. A list given with no entry is the empty list, never a constraint left out: an `sh:in` or an `enum` with none allows no value (see [Values](#values)).
- A template node (a target, a `hydra:search` or a template-named key's value with a `hydra:template` or typed `hydra:IriTemplate`) with no template it reads is a problem: its own IRI is never sent to, and the control's other target is not a fallback. A value of a term typed `@json` is a JSON literal, never an address, a method or a node, and a JSON literal under `hydra:expects` is read only when it holds a JSON Schema (an object whose `properties` is an object, or whose keys are all JSON Schema keywords, one or more of which constrains, such as `{"type": "object", "additionalProperties": false}`), whose `required` must be a list of names and each `enum` a list. An object written in place under `hydra:expects` is read as a JSON Schema by the same test, so a body schema with no properties is checked as one, not passed over as a shape the document does not describe; anywhere else an object is read as JSON-LD, whatever keys it has, so a node written inside one that has `properties` is read, hints and all. A JSON Schema written in place is not read as JSON-LD, so one that holds what JSON-LD reads there is refused whole, naming it, and a hint written there is never passed over: a JSON-LD keyword at its top other than its own `@id` and `@type` (`@included`, `@graph`, `@context`, `@language`, `@index`, ...); a node (an object with an `@id`, with a key the context expands, or with a keyword that holds nodes) under a key that is no JSON Schema keyword, or under a JSON-LD keyword, in it or any schema inside it; a JSON Schema keyword (`default`, `examples`, `properties`, `title`, ...) in it or any schema inside it that the document's context gives a meaning, by a term of that name or by `@vocab`, in the context where the schema sits or in the one JSON-LD reads its own keys in (the one before a type's scoped context that does not propagate, then the scoped context of each type the schema itself names), so JSON-LD reads it as a property, and what is under it, a node and its hints, or what it says of the schema's own `@id` (`This document writes "default", a key its @context gives a meaning, in a JSON Schema, ...`); a schema written in place in a document that names a remote `@context`, which may give any keyword a meaning and which neither client fetches (`This document names a remote @context, ...`); and a key that is no JSON Schema keyword and that the context expands, which JSON-LD reads as a property of the schema's node, or of the node its own `@id` names (`This document writes a node under "iep:x" in a JSON Schema, which this client does not read as JSON-LD, so it is not read.`). A `sh:path` that is a blank node, or an inverse, alternative or repeated path, is a problem, not a field.
- An object that names a node by its `@id` (aliased, compact or relative) is read as that node, every description of it merged, never as the object itself: a control's `annotations`, a template's mapping, a shape's `sh:property`, a class's `hydra:supportedProperty`, a template or a list. So is a string that names one, as JSON-LD reads a string under a term typed `@id` or `@vocab`, alone or in a `@list`; where a control's hints are read, a string under any term that names a node the document describes counts, typed or not, since reading more hints can only make a control less safe. One the document does not describe is a problem where it decides safety, the address or the inputs: annotations (an object or a string), a mapping, a property or a supported property it does not describe, and a target, a `hydra:expects` or an `sh:in` that is a blank node it does not describe. A field of a control's own `fields` list that names a node, and a JSON Schema property written as a reference (`$ref` or `@id`), are refused rather than read; a schema inside a property's written so (`"items": {"@id": "#E"}`) is a constraint neither client checks, so a value given for the property is refused (`m: has a constraint this client does not check (items/@id), so it is not sent`). A field written in place, in a control's `fields` list or a HyperMarkdown block's, says what the substrate's HyperMarkdown lift writes (`name`, `path`, `datatype`, `minCount`, `maxCount`, `minLength`, `maxLength`, `pattern`, `defaultValue` and `description`); one that gives any other key, such as `in` or `minInclusive`, is refused with the key named, never read without it. It is read as the lift reads it into a property shape: a default that is a number or a boolean is its text, `rdf:JSON` takes JSON, `maxCount` 0 takes no value, and a `minCount` or `maxCount` above 1 makes a list. A count or a length is a JSON number that is a whole number of zero or more; one that is not (`1.5`, `"3"`, `-1`, `true`, one past 2^53), which the lift drops, keeps the control from being invoked, as a shape's count that is not a whole number of zero or more does. Beside a shape `hydra:expects` names that the document describes, the shape's fields are the inputs, and each field written in place must be one of them and agree with it on each key it gives, or the control is not invoked. A node the document describes with no input fields (a shape with no properties, a class with no supported property) is described too: no field written in place is one of its inputs, its `sh:closed` is read, and a warning says it gives no input fields. Where no node with that `@id` is in the document (a HyperMarkdown block never describes one), the fields written in place are the inputs, with a warning that what else the server expects is not known. Each is read one level deep, so references that loop cost nothing more.
- A property with no value is absent: null and `[]` are no value, while `{}`, `false`, `0` and `""` are values, alike in both clients. The exception is a SHACL list parameter (`sh:in`, `sh:or`, `sh:and`, `sh:xone`, `sh:languageIn`), where `[]` or a list of nulls is the empty list: an empty `sh:in`, `sh:or`, `sh:xone` or `sh:languageIn` allows no value, and an empty `sh:and` asks nothing (see [Values](#values)).
- A value a link (`field.<name>=`) or `--field` gives is checked as it was given, never as a form control would change it, and is never replaced by a default: a choice that is none of the options, a number field given text or only spaces, a boolean given anything but `true`, `false`, `1` or `0` (trimmed of space, tab, CR and LF, so `yes` and `TRUE` are no boolean), and a list given only blank lines are refused by name; a list's values are checked in order, and its check stops at the first one with a problem, which is the one named; a multiple choice is sent in the order and number given; a line break or carriage return in text is kept. An empty value is no value, as an empty input is: `field.scope=`, `--field scope=`, a repeated one whose last value is empty, an input you clear, and a form you do not touch all send the default as the document gives it, or nothing where there is none, so the four never differ. A default of empty text is a value the document gives: it is sent as empty text, and refused by name where an address would leave it out or the field reads no value in it (a number, a boolean, JSON). A default is checked as a value given is, so a number field's default of only spaces, and a list's default whose entries are all blank or that is empty text, are refused by name (`m: its default holds no values, so it is not sent`); so is one of another kind than its field takes (see [Values](#values)). The page invokes its form with a link's values, as given, until you change the input one fills, and shows a value with a line break in a text area. A number field is a text input. A default is shown in the form only when what the form then holds is read, with no problem, as the same value as the default itself; otherwise the field is left empty and the default itself is checked and sent, required or not, since the form leaves validation to the page's own checks, which name each problem. A link that invokes is refused, naming the parameter, when it carries one the page does not read (anything but `url`, `invoke`, `dry`, `query`, `autoload` and `field.<name>`), as `hmc.py` refuses an option it does not know.
- A field takes a value under its name, its template variable or its path's local name. A control where one of those names is another field's (its name or one of its other names) is refused, since which input a value fills is not known. A descriptor address is checked as it is given too: one with a tab, a line break or a space in it is refused, where the page's address field and Python's `urlsplit` would drop the character.
- A title, label or description is only shown, so the first value that reads as one is shown.
- Read: node objects and `@id` references; value objects with `@type`, `@language` or `@direction`; a `@json` schema under `hydra:expects`; keyword aliases, `@nest`, embedded and scoped contexts and container maps; a `@set` object anywhere the document's JSON-LD is read, as what it holds (inside a JSON Schema, whose keys are not JSON-LD, a JSON-LD keyword is refused instead: see [Values](#values)); a `@list` or graph object where operations, a shape's properties or a template's mappings go, as its members; a `@list` under `sh:in`; `@graph` and `@included` at the top or inside another `@graph`. A remote `@context` is not fetched: the clients' own names for Hydra and Interego terms (`method`, `target`, `action` and the rest) stand in for it, and are used before `@vocab`, so a document that leaves one of those names to `@vocab` is read as naming the Hydra or Interego term.
- Refused whole, with the problem named: `@reverse`; a `@graph` or `@included` inside a node, and a term whose values are graphs (`"@container": "@graph"`) anywhere but where operations, a shape's properties or mappings go; `@import` in a context, which a JSON-LD processor fetches; a `@set` object with another key, inside a `@list` or with a `@context` of its own; a keyword given twice in one node, through an alias or a `@nest`; another keyword inside a `@nest`; and a key repeated in one JSON object. When the refused document is the JSON-LD a `?format=jsonld` retry answered, the HyperMarkdown or Turtle answer it was asked for instead of is listed with the problem named, and none of its controls is invoked (see [How target resolution works](#how-target-resolution-works)).
- A HyperMarkdown block is read line by line, a line ending being CR LF, CR or LF and nothing else, with each key and value trimmed of space and tab only. A block that gives `rel`, `method`, `target`, `expects`, `mediaType` or `fields` twice, writes one of the first five as a JSON array or object, writes `fields` as anything but a JSON array of objects (read as a document's JSON is, so `NaN` and a repeated key are not JSON), or has two fields of one name is refused. A name that matches two controls, a link with two `url` or `invoke` parameters, and values given under two names of one input are refused too.
- A field's name is used as written: one with a line break in it is never shortened. The page matches each input of a form to its field by position, so a name holding a character HTML rewrites in an attribute, such as CR, is still the field's.

## Work

Each thing a person asks of a document is one step of work: reading it, listing it (`list`, `list --json`, the page's list), opening one of its controls (the page's form, `describe`, and `invoke` before it checks a value), checking the values given, and building the request. Both clients count a step's work alike, in units, against one budget for the step: 64 units for each byte of the document's text as received (in UTF-8), and 2,000,000 at least; checking values may also cost 64 units for each byte given, and building a request 64 for each byte of the values it sends, as JSON writes them.

- A unit is a UTF-16 code unit of text: each IRI a prefix, a term, `@vocab` or `@base` expands to as the document is read; the text a control carries (its `@id`, name, method, title, description, media type, what it expects and returns, its target or template, its types, and the problems reading it gave) each time it is read, shown or written; the text a field carries (its name, path, datatype, pattern, description, default and each entry) each time it is shown or written; what each template expression expands to, each variable's part charged as it is made, before any is joined, so one expression that names a variable many times, or an exploded list that writes a long name once for each value, stops where the budget does; and the address and body of a request.
- And a fixed number: 16 for each control read or shown, 8 for each field a control uses, however many controls share it (a template's fields, a property node many shapes name), and for each field shown, and 1 for each value checked.
- A node that many controls, inputs or mappings name (an annotation node, a target or template node, a mapping node, a property or `hydra:property` node, what a `sh:node`, `sh:path` or `sh:in` names, a closed shape, and an RDF list, such as one that many closed shapes name as their `sh:ignoredProperties`) is read once for each document: its keys, its hints and what its values for each property read as are kept, so naming it again costs a constant, not its size again. The hints its own keys give are charged once, 1 unit for each of its keys and each hint value, and 1 more for each control that names it; the text of the values a problem lists, where a property has more than one, is charged each time the problem is written.
- Past the budget the step stops, nothing of it is shown, written or sent, and it is refused by name: the document as it is read or listed, the control as it is opened (the page shows no form, `describe` writes `"fields": null`, `invoke` exits 2), the request as it is checked or built: `This document asks for more work than its size allows (N units for M bytes); nothing was sent.` The limits named above ([How target resolution works](#how-target-resolution-works), [Fail closed](#fail-closed), [Values](#values)) are checked first and name their own problems; the budget is the backstop for every other way a small document could make a step cost far more than its size.
- Turtle, which `hmc.py` hands to `rdflib`, is charged first, in the step that reads it, for what `rdflib` would make of it before this client reads a byte: the text is read as `rdflib`'s parser reads it, comments, strings and IRIs whole, and each prefixed name is charged the longest expansion of any prefix declared so far, each relative IRI (and each `?` variable) the longest base so far, and each prefix or base declared all its text could resolve to, against the IRI budget above (`This document's prefixes, terms, @vocab and @base expand its IRIs to far more text than the document holds, ...`); and each term (a word but a closing `.`, an IRI, a string, and each `[`, `(`, `!` and `^`), of which `rdflib` makes and keeps a node or a triple, costs 256 units. So a long prefix or base, one declared again and again, or a long list of short values is refused before `rdflib` reads it, with or without `rdflib` installed. `hmc.py` names running out of memory: `error: This needs more memory than this process has, so it was stopped.`
- `hmc.py`'s `list` and `list --json` write for every control what the page's list does not show (its target, its fields, its problems), so they can refuse a document the page lists. The page decides whether its form shows a default without charging the step, as `hmc.py` has no form.
- What either client shows of a response grows with its size, never with a product of its parts: it reads at most 8,388,608 bytes of one (past that it shows none of it and says so), and lays one out (the page's table of a SPARQL result, indented JSON) only while the layout adds at most 8 units for each of its bytes, and 10,000 at least, a unit being a character a table cell shows or a character of indentation, and each cell of a table, its head's and each row included, counting 9 units besides, the markup of an empty one (`<td></td>`), so a table has fewer elements than its response has bytes, however few of them it shows; past that it shows the response as its text after a note naming why, and JSON it writes of its own (the page's request, `hmc.py`'s `--json`, `list --json` and `describe`) is written unindented. The page's table reads each binding by its own keys, through its columns mapped once from the result's head, so a variable's name costs its length once, not once for each row. `hmc.py`'s `invoke --json` gives that note as `response.note`, which is there only when there is a note; `response.bodyText` and `response.body` are null for a response past 8,388,608 bytes, and `response.body` is null for JSON shown as its text.

On the live catalogs below (11 documents and 600 controls on 2026-11-18: the JSON-LD and HyperMarkdown answers of the i2idlx catalog and the Foxxi, PEV, WRD and WSP affordance manifests, and the catalog's Turtle address), the most any step of JSON-LD or HyperMarkdown used was 2.1% of its budget: reading Foxxi's manifest. Reading the catalog's Turtle address (101,753 bytes on 2026-11-18) with `rdflib` 7.6 used 16%, nearly all of it the 256 units for each of its 3,400 terms.

## Values

A confirmed write sends what the form validated, and both clients check a value alike: the same constraints, the same verdicts, the same problems in the same words. Each constraint is applied to the kinds of value its standard applies it to; a constraint neither client checks refuses the value by name instead of sending it; and a keyword written in a form its standard does not allow keeps the control from being invoked.

- An enumeration (JSON Schema `enum` or `const`) holds JSON values of any kind, and a value is in it when it is the same JSON value as an entry: arrays item by item in order, objects by the same keys with the same values in any order, numbers by value (`1.0` is `1`, `-0` is `0`, and an integer past 2^53 is the double `JSON.parse` reads, as both clients read every JSON number), and a string, a boolean or null only the same of its kind (`"1"` is not `1`, `true` is not `1`). So `{"type":"array","enum":[["allowed"]]}` refuses `["not-allowed"]`. An entry that holds an integer past 2^53 at any depth, which `JSON.parse` may have rounded, is not surely the number the document wrote, so it matches no value, in an `enum` or a `const` at any depth and in a shape's `sh:in` or `sh:hasValue`: a value that would match only it is refused, naming it (`m/0: matches only 9007199254740993, which holds an integer past 2^53 that reading JSON may have rounded, so it is not sent`). So is an entry that holds a number the document writes anywhere with more digits than its double keeps (`0.30000000000000000001` reads as 0.3, so in that document an entry 0.3 matches no value: `m: matches only 0.30000000000000000001, which holds a number that reading JSON may have rounded, so it is not sent`). A problem names each such number, an entry, a const, a bound or a `sh:hasValue`, as the document writes it, never as the double reading it gave: `9007199254740993`, not `9007199254740992`; `1e-400`, not `0`; `1e400`, not `null`; and, where the document writes two or more numbers that read as one double, each of the first two, joined by `or`, and an `rdf:JSON` entry whose text holds a number its double would change.
- A JSON Schema field's select offers each entry its type can take, written as its JSON when it is not a string (`["x"]`, `{"k":"v"}`, `true`, `1`, `null`), and a choice is sent as the entry it names, never as the text that names it: in a property with no type, choosing `{"k":"v"}` sends that object and `1` the number. Null is a choice of its own, sent as JSON null, apart from the blank option, which sends nothing. Two entries written alike (`"true"` and `true`) leave which one a choice means unknown, so the control is not invoked. An entry that holds a number no double holds (`1e400`) is not offered, nor, in any field, one that is an integer past 2^53, or a number the document writes with more digits than its double keeps, which `JSON.parse` may have rounded: neither is surely the number the document wrote, and in a number field with an enum or a const a value that is an integer past 2^53 is refused (`integer too large to send exactly`), since the entries it would match are doubles. An entry of empty text is not offered either: the blank option writes it, and an empty value is no value. A default is a choice only when the choice its text names is the same JSON value: `{"enum":["1"],"default":1}` leaves the select empty, and the default itself, the number 1, is checked and refused, never sent as the string `"1"`; `{"enum":[1],"default":"1"}` is refused the same way. A field typed as JSON (an array, an object, or both) takes JSON text and shows its entries in its hint; its type may also admit `null`. In `hmc.py` the choice is `--field name=<text>`.
- JSON Schema applies a type, an enum and a const to every value; a length only to a string (counted in code points); `minimum`, `maximum`, `exclusiveMinimum` and `exclusiveMaximum` (a number, or draft 4's `true` beside a bound) only to a number, and only where that number is surely the one the document writes, as below; `minItems`, `maxItems` and `items` only to an array; and `required`, `properties` and `additionalProperties` only to an object. Both clients apply each the same way, at every depth of a JSON value, and name where a problem is as a JSON Pointer after the field's name (`doc/tags/0: longer than maxLength 3`; a name that holds `/` is set apart from it, as in `d/x at /0`). The first problem found in a field's value is the one named, and the check of that value stops there, so a long value with many bad parts costs its size once and names an enum's entries once; each enum's entries and each const are keyed once per check, so comparing a part with them costs that part's size, not theirs. A shape's `sh:hasValue` and bounds are read once for all a field's values too, so a long one costs its length once, however many values a list holds. `readOnly: true`, which says the value is not the client's to write, refuses a value at any depth, as `hydra:writable` false does below, and such a property is never given its default; on the schema of the whole body it keeps the control from being invoked. A type of an array and an object refuses a value that is neither. A union of types with no string and no choices, other than numbers alone, is no one input, and is refused. `format` and other annotations describe and are passed over, as JSON Schema passes over them; `pattern` is shown and left to the server, as above.
- A JSON Schema keyword that constrains a value and that neither client checks (`allOf`, `anyOf`, `oneOf`, `not`, `if`/`then`/`else`, `multipleOf`, `uniqueItems: true`, `contains`, `prefixItems`, `items` as a list, `unevaluated*`, `minProperties`, `maxProperties`, `patternProperties`, `propertyNames`, the `dependent*` keywords, `$ref`, and a JSON-LD keyword written in a schema, which JSON Schema does not define: a schema written as a reference to a node, `@id`, or wrapped in `@set`, `@list`, `@graph` or a `@value`, which is not read as what it holds there) is named where it is, and a value given for that property is refused with its name; on the schema of the whole body, the control is not invoked, and so is it for an `enum` or a `const` there, which constrain the body as a whole. At the top of the body's schema, a JSON-LD keyword is no keyword it reads: written in place, the schema may keep its own `@id` and `@type`, and any other refuses the document (see [Fail closed](#fail-closed)); a JSON literal's schema is JSON, so any there, `@type` and `@id` included, keeps the control from being invoked (`the JSON Schema names @type, which this client does not check, ...`). So is a body schema that describes something other than an object, or requires a name it does not describe. A keyword in a form JSON Schema does not allow (a type that is not a type name, a length that is not a whole number, a bound that is not a number, a `readOnly` that is not a boolean, an `allOf`, `anyOf`, `oneOf` or `prefixItems` that is not a list of one schema or more, such as `[]`) keeps the control from being invoked; a length or a bound written as text, such as `"5"`, is not a number, and is not read as one.
- The body carries the properties' values and a template's variables that are no property's, which go in the address and the body alike. Where the body schema names `additionalProperties`, that is such a variable's schema: `false` refuses a value given for it (`q: is not allowed by its schema`), and a schema types and checks it as it would a property; it is read once for all such variables. Where the body is a SHACL shape's with `sh:closed` true, with properties or none, a value for such a variable is refused (`q: is not allowed by its shape, which is closed (sh:closed true), so it is not sent`) unless `sh:ignoredProperties` names its property.
- One list of choices is offered, and named in a problem, by one input, so that neither costs more than the document's size: choices in an `additionalProperties` schema (an `enum` or a `const` at any depth) that two or more template variables would take, and one RDF list that is the `sh:in` of two inputs, keep the control from being invoked, and an RDF list that shares nodes with another list is not read. So does a default, a description or a pattern in an `additionalProperties` schema that two or more template variables would take, which each would show, and a default send, once for each (`the inputs "v0" and "v1" share the default of additionalProperties, ...`). An RDF list is read once however many values name it.
- A shape's `sh:in` and `sh:hasValue` name RDF terms, read as their text, each field's `sh:in` once however many values it checks: a number field's value is the entry that is the same number of its type, an rdf:JSON field's the entry whose text is the same JSON value, and a node value (a JSON object or array) is none, since no IRI or literal is a node. `sh:hasValue` makes its input required, and a list holds it among its values. A list is given when it is written at all, so an empty one is read as SHACL and JSON Schema read it, never as no constraint: an `sh:in` written as `{"@list": []}`, as `[]`, as `rdf:nil` (an IRI or a compact one, which is the empty list and never an entry) or as a list of nulls JSON-LD drops allows no value, given or default (`status: its shape allows no value (sh:in is empty), so it is not sent`), and so do an empty `sh:or`, `sh:xone` and `sh:languageIn`, while an empty `sh:and` asks nothing; an `enum` with no entry allows no value at any depth of a schema (`m/0: its schema allows no value (enum is empty), so it is not sent`), while an empty `required` asks nothing and a `const` of `null` allows null alone. An input that is required (by `sh:minCount`, `sh:hasValue`, `hydra:required`, a template's mapping or a schema's `required`) but allows no value, by such a list or by `sh:maxCount 0`, keeps the control from being invoked (`the input "status" is required, but its shape allows no value (sh:in is empty); this control is not invoked`); one that is not required takes nothing and sends nothing, and the page offers no choice for it, so no empty select sends `""`, and says in its hint that it allows no value. `list --json` names an empty `sh:in` or `enum` as the field's `in`, an empty list in `inLists`, never `null`, which says it names none. A zero is a number as any other: `sh:maxCount 0`, a length, a bound or a count of 0 and a default of `0` or `false` are checked, never passed over. A SHACL length facet measures text (a literal's, or an IRI's); a JSON value in a field has no one text it measures, so a value given is refused, while a body sent whole is measured as it is sent. Bounds, inclusive and exclusive, compare numbers, on a field whose datatype is an XSD number: a value that is no number is refused, and so is any value for a bound that is not a number (a date), which neither client compares, or for a bound on a field of any other datatype (text, an IRI, a date, or none), which SHACL compares with the value's own datatype, never with the number its text reads as (`m: its sh:minInclusive 3 bounds a field that takes no number, ...`). A bound past what a double holds is an infinity, which still bounds every number a value can be. A bound whose number may not be the one the document writes is not compared, so any value is refused, naming it: text with more digits than a double keeps (`"0.30000000000000000001"`, `"9007199254740993"`), a JSON integer past 2^53, or a JSON number the document writes anywhere with more digits than its double keeps, in a shape and in a JSON Schema's `minimum`, `maximum` and exclusive bounds alike (`m: its sh:minInclusive 0.30000000000000000001 is a number a double may not hold exactly, which this client does not compare, so it is not sent`); one written exactly is compared, trailing zeros and all (`"0.50000"`). `sh:maxCount 0` takes no value, given or default (`m: takes at most 0 values, got 1`), and a negative count or length is no whole number, which keeps the control from being invoked.
- Datatypes checked: `xsd:string`, `xsd:anyURI`, `xsd:boolean`, the XSD numbers, each integer type within its range (`xsd:byte` from -128 to 127, `xsd:positiveInteger` from 1) and none past 2^53 - 1, which a JSON number cannot carry exactly (`integer too large to send exactly`, whatever the type's range or the field's bounds), the XSD 1.1 dates and times, and `rdf:JSON`. A double or a float is read as the double nearest its text, and a float past the largest float (about 3.4e38) is refused as out of its range. A decimal, a double or a float whose number is a whole one past 2^53 - 1 is sent as JavaScript writes its double, in an address and a body alike (`123456789012345680000`, never the double's exact integer, `123456789012345683968`). A value for any other datatype (`xsd:language`, `xsd:token`, a language-tagged string) is refused by name, since its form is not checked.
- Dates and times are checked, not refused: `xsd:date`, `xsd:dateTime`, `xsd:dateTimeStamp`, `xsd:time`, `xsd:gYear`, `xsd:gYearMonth`, `xsd:gMonth`, `xsd:gDay`, `xsd:gMonthDay`, `xsd:duration`, `xsd:yearMonthDuration` and `xsd:dayTimeDuration`, each against its lexical grammar in XSD 1.1 Part 2 and its value constraints (a duration against the regular expression the spec gives for it, so a fraction of a second has digits on both sides of its point: `PT1.5S`, never `PT1.S` or `PT.5S`, which the grammar's productions would allow), by the same hand-written steps in both clients (no pattern from a document is run): a year of four digits or more, with no leading zero past four and an optional `-`, `0000` included as XSD 1.1 allows; a month from 01 to 12; a day no later than its month's last, 29 February only in a leap year of the proleptic Gregorian calendar (2000 and 0000 are, 1900 is not) and in any `gMonthDay`; an hour from 00 to 23, or `24:00:00` exactly; minutes and seconds from 00 to 59, and a fraction of a second of one digit or more; a timezone of `Z` or `+hh:mm`/`-hh:mm` no more than 14:00 from UTC, which `xsd:dateTimeStamp` requires; and a duration of one part or more in the order `Y M D T H M S`, a fraction on the seconds only, `T` only before a part of the time, only `Y` and `M` in a `yearMonthDuration` and neither in a `dayTimeDuration`. Digits are ASCII digits, and no space is trimmed. A value that is one is sent as typed; any other text is refused naming the datatype (`day: not an xsd:date`). Their bounds are not compared, since XSD orders a value with a timezone and one without only in part, so a value for a date field with a bound is refused by name, as above. A JSON Schema `format` (`date`, `date-time`, `time`, `duration`) stays an annotation, as JSON Schema has it, and is passed over.
- A default is checked as the document gives it, and must be of the kind its field takes: in a JSON Schema field its schema decides, on the value as written, never trimmed, read as a number or a boolean, or parsed as JSON (`{"type": "string", "default": 1}` refuses the 1, `m: must be a JSON string`, `{"type": "number", "default": "5"}` refuses the "5", `m: must be a JSON number`, and a property with no type sends an object default as the object), and a default of `null` is sent as JSON null where its schema allows null and refused where it does not; in any other field that does not take JSON, a default is text, or for a number or a boolean field that value or its text (a boolean's being XSD's: `true`, `false`, `1` or `0`, so `"yes"` is refused), and one of another kind is refused by name (`m: its default 5 is not text, which this field takes, so it is not sent`), in a list item by item, never sent as another kind of JSON nor changed into its text. A list's default is sent with all its values or not at all: one with a blank value among others is refused (`m: its default holds a blank value, which this client neither drops nor sends, so it is not sent`). A field written in place gives a number or a boolean default as its text, since the lift reads it so. A default that holds a number reading JSON may have rounded is refused at any depth, in every field but a double's or a float's, which takes the double nearest: an integer past 2^53, or a number the document writes anywhere with more digits than its double keeps, since reading JSON gives each client the double, not the digits (`0.30000000000000000001` reads as 0.3, so in that document a default of 0.3 is refused too) (`m: its default holds a number that reading JSON may have rounded, so it is not sent`). JSON text given for a field, or written as its default, that holds a number its double would change is refused naming the number (`m: holds 9007199254740993, which a JSON number would change, so it is not sent`), and one its double holds is sent as JavaScript writes the double (`1.0` as 1); a body sent whole is sent as written.
- JSON nested deeper than 256 arrays and objects is not read, in either client: a value given is refused by name (`data: nests JSON deeper than 256 levels, ...`), a document is refused whole, a HyperMarkdown block's fields keep its control from being invoked, and a response is shown as its text. So no JSON costs more than a fixed amount of call stack or of indentation per item, in reading it or in sending it. `sh:nodeKind` is checked as the client sends: text that is an absolute IRI is an IRI, other text a literal, a JSON value a node, and an `rdf:JSON` value a literal, whatever JSON it holds; a field that holds its values as one JSON array (a node-valued property with no `sh:maxCount`) checks each item. `sh:class`, `sh:or`, `sh:and`, `sh:xone`, `sh:not`, `sh:languageIn`, `sh:uniqueLang`, `sh:sparql`, a property shape's own `sh:property`, and `sh:closed` (unless false) cannot be checked here, so a value given is refused with the name (an empty `sh:or`, `sh:xone` or `sh:languageIn` allows none, and an empty `sh:and` asks nothing, as above); so is one for `sh:node` unless the shape it names constrains nothing. `sh:qualifiedValueShape`, `sh:equals`, `sh:disjoint`, `sh:lessThan` and `sh:lessThanOrEquals` relate an input to others, and a shape-level `sh:or`, `sh:and`, `sh:xone`, `sh:not`, `sh:node`, `sh:class`, `sh:sparql` or `sh:qualifiedValueShape` constrains the whole body: each keeps the control from being invoked, but an empty shape-level `sh:and`, which asks nothing. A shape with no properties whose own value constraints (a datatype, a length, `sh:in`, `sh:hasValue`, a bound, `sh:nodeKind`, `sh:pattern` or `sh:languageIn`) describe the body makes one input of the body sent whole, checked against them as an input is; on a shape that has properties, each of those keeps the control from being invoked, since no input checks the body as a whole. `sh:pattern` and its `sh:flags` are left to the server, as above.
- A `hydra:supportedProperty` whose `hydra:writable` is anything but true is not written: a value given for it is refused. `hydra:readable` says what a client may read, and is passed over when sending.
- A value that goes in the address (a template's variable, or any value of a safe method, which sends no body) is refused where the address would leave it out: null, `""`, a list with no items or with a null or `""` in it, and, in a template, any value RFC 6570 reads as undefined (`{}`, `[[]]`) or an object with a member it drops. A query writes an object as its JSON, whole. A body carries every JSON value as it is.

## Safety

- GET / HEAD / OPTIONS are treated as safe and may be sent.
- POST, PUT, PATCH, DELETE, anything with `iep:destructiveHint true`, or `iep:readOnlyHint false` is unsafe. So is a control that names no method: it is a POST, as the substrate's own follower sends it. Every value of a hint counts: a `destructiveHint` true or `readOnlyHint` false under any prefix, in an object written directly inside the control (MCP's `annotations`), on the node such an object names by its `@id` or a string names, wherever the document describes it, or in a HyperMarkdown block makes it unsafe, and so does a hint that is not a boolean (`true`, `false`, `1`, `0` or an `xsd:boolean` literal). True and false together refuse it. Neither hint ever makes a control safe.
- Unsafe operations default to a dry run that prints the exact URL, headers, body, and MCP call. The web UI requires an explicit checkbox before Invoke is enabled. The CLI requires `--confirm`. A confirmed write is sent to that URL and nowhere else (see [Writes go where they say](#writes-go-where-they-say)).
- Only a 2xx answer is a success. After an invoke each client names the address and the status, and where a GET or HEAD was redirected to, in one of three outcomes: `Done:` for a 2xx; `Not done:` for a 301, 302, 303, 307 or 308 that the request did not follow (every write, and every method but GET and HEAD; see [Writes go where they say](#writes-go-where-they-say)); and `Not a success:` for any other answer, a 300 or 304, or a redirect with an empty `Location` answered to a safe GET or HEAD, included. `hmc.py` exits 0 for a dry run or a 2xx answer, 3 when the control has no plain-HTTP transport and nothing was sent, and 4 for any other answer, in text and `--json` mode alike; `--json` also gives `done` and `outcome`, the same words.
- The URL a dry run shows is the one sent, as the URL Standard's parser writes it: lower-case scheme and host, no default port, dot segments removed (`%2e%2e` is `..` to the parser), the characters it percent-encodes encoded, no fragment, and fields added to the query as `URLSearchParams` writes them (`~` as `%7E`, `*` as it is). The page has the browser's parser write it; `hmc.py` writes the same string. An address a parser reads differently from its text is refused before anything is sent: one with a backslash, a space or a control character; `http(s):` with no `//` before the host; user information before an `@`; a host that is neither a name of letters, digits, `.`, `-` and `_` nor a bracketed IPv6 address; a port that is not a number up to 65535; or a host written as a number in any form other than four decimal parts (`0x7f.1`, `2130706433`). `hmc.py` also refuses a host with ß, ς, ZWJ or ZWNJ, which Python's IDNA 2003 sends to another domain than a browser does (`straße.example` is `strasse.example` to one and `xn--strae-oqa.example` to the other).
- The web app shows everything a remote document or response contains as text. An HTML response is shown as source, not rendered. Only an `https` URL becomes followable, and following one fetches it as a descriptor; an `http` IRI is shown as text. Nothing a remote document sends becomes a link the browser navigates, a script, a style, an event handler, or a form field's `name`.
- The page sends requests over `https` only, with or without a proxy, and does not hand a proxy an internal address (see [The proxy field](#the-proxy-field)).
- Next to **Invoke**, the page names the host the control sends to, or says that a template decides it when a template variable comes before the host is complete, and the dry run shows where. A named host is checked against the address before anything is sent.
- The page does not run inside another page's frame. Open it in a tab of its own.
- A control that cannot be drawn shows a warning and no form, and a form only ever invokes the control it was built for.
- `hmc.py` sends requests to `http` and `https` URLs only, and follows a redirect only to another of those. A descriptor that names a `file:`, `ftp:` or `data:` URL, or a redirect to one, is refused before anything is read.
- In text mode, `hmc.py` shows control characters in remote text as `\xNN` escapes, so a document cannot send the terminal control sequences. `--json` output escapes them as JSON does.
- The page carries a Content-Security-Policy: no source by default, its own inline script and stylesheet allowed by SHA-256 hash only, no inline event handlers, `connect-src https:`, and `object-src`, `base-uri` and `form-action` set to `'none'`. Editing the inline script or `<style>` changes its hash, so the policy has to be updated with it; `tests/hypermedia-client-rendering.test.ts` fails and prints the expected hash when they disagree. That test also loads the page with hostile documents and responses and checks what reaches the DOM.
- Do not live-invoke write controls such as `act-propose-mapping`, `act-ratify`, `act-publish-classified`, `act-align-course-concept`, `write-xapi-statements-signed`, `act-request-upstream-review` (it opens a GitHub issue form), or `coverage-query`.

### Writes go where they say

A request goes only to the address its dry run shows. A confirmed write, and any request other than a GET or HEAD, never follows a redirect (301, 302, 303, 307 or 308) in either client: `hmc.py` sends it with no redirect handler, and the page sends it with `fetch`'s `redirect: "manual"`. Followed, a 307 or 308 would send the write again, body and all, to an address nobody confirmed, and a 301, 302 or 303 would turn it into a GET there.

A redirect answer is reported as not done, in words both clients share: the address answered with a redirect; the request was not re-sent (nor turned into a GET, where `fetch` would have turned it into one: a POST on a 301 or 302, anything but a GET or HEAD on a 303, and any request on a redirect whose status the page cannot see); and whether the address acted on it is not known. `hmc.py` names the status and the `Location`, resolved against the address, prints them in text mode and gives them as `redirect` in `--json`, and exits 4. It reads only the headers of a redirect it does not follow, as the page's opaque redirect has no body, so `--json` gives `bodyText` as `""`, and a redirect whose body never ends is reported at once. The page gets an opaque redirect, which shows neither, and says so; when the `Location` is empty, which Chromium does not read as a redirect, it sees the status and names it. A 3xx that is not a redirect status (300, 304) is an answer that is not a success.

In a browser a cross-origin answer goes through the CORS check before the redirect mode applies, so a redirect without `Access-Control-Allow-Origin`, like any other answer without it, makes `fetch` fail, though the host received the request. The page does not call such a request refused: for a request it sends without following, it says that no answer it can read came back, that the request may have reached the address (a redirect, or any answer without CORS headers, reads this way, as a network error does), and that whether the address acted on it is not known.

A GET or HEAD from a control listed as safe follows redirects as a descriptor load does, alike in both clients: over `https` only on the page, `http` or `https` in `hmc.py`, at most 20, a redirect to another scheme refused, and one with an empty `Location` not followed. Each hop is the request `fetch` sends: a HEAD stays a HEAD and a GET a GET on a 301, 302, 303, 307 or 308 (`urllib` before Python 3.13 sends a HEAD on as a GET, which `hmc.py` does not let it do), with the same `Accept` and no body, and a HEAD's answer has no body, whatever the host sends. A redirect is followed on its headers; its own body is not read. Given an HTTP proxy in its environment, `hmc.py` sends that proxy's `Proxy-Authorization` only on a hop through the proxy, never to a host it reaches directly, as a browser never sends one to a host. Its outcome names the address it landed at, as `fetch` writes it: `hmc.py` resolves the `Location` and sends it as it writes a request URL (see [Safety](#safety)), so the address has no fragment and `{`, `}` and the backtick are percent-encoded, as in the page's `res.url`. A `Location` that a URL parser reads otherwise than its text, which `hmc.py` refuses as an address (a backslash, a space, a control character, user information, a host written as a number), is a redirect `hmc.py` refuses too, naming it, and nothing is sent there. The page cannot see a `Location` before its browser follows it, and the browser follows such a one as its URL parser reads it: a backslash as a slash, so `\\other.example/x` leads to another host. OPTIONS is safe but is not followed: a 303 would turn it into a GET.
